### Fixed
- **BUG-006 (medium)** — the fixture generator wrote exactly one bitmap block and panicked on any volume above about 2 MB, where a second is needed. An 8 MB hardfile needs five. Every fixture until now was a floppy, comfortably inside one block, so the limit only appeared when Phase 2 asked for a volume large enough to matter. `write_bitmap` now allocates as many as the geometry needs and fills the rootblock's `bm_pages`.
- **BUG-005 (high)** — reading a hard link returned `Ok("")`, an empty file, silently. A link block holds no data; `real_entry` names the block it stands for, and that field was parsed but never used. Found on the first Phase 2 task by checking what the existing code already did with a link, rather than by a test — the corpus has no links and the generator could not build one.
- **CI toolchain drift.** `rust-toolchain.toml` said `channel = "stable"`, so CI installed whatever the runner had (1.98.0) while local development sat on 1.94.1 — four releases apart. With `-D warnings`, a lint added in any of those releases breaks the build with no code change, which is exactly what happened: `unnecessary_sort_by`, new in 1.98, rejected a reverse sort that passed locally. The toolchain is now pinned to an exact version, and a non-blocking `toolchain-drift` job lints against latest stable so falling behind surfaces as a warning rather than a red build.
- **BUG-004 (medium)** — the fixture generator wrote the bitmap checksum at offset 20, where every *other* block type keeps it, overwriting the map words covering blocks 130–161. Bitmap blocks are the one exception: checksum at 0, map from 4. It hid because the normal checksum makes the whole block sum to zero, so validation passes wherever the field sits; only the layout differs. Surfaced by fixtures reporting 27 orphaned blocks where real disks reported none — D-010's two mechanisms catching the *generator* rather than the parser, which is the direction I had not anticipated.
- **BUG-003 (high)** — `read_file` reserved `Vec::with_capacity(byte_size)` from a `u32` read straight off the disk, so a crafted header made ADE attempt a 4 GB allocation on an 880 KB floppy before reading anything. AV-005 in one line, on the plain ADF path rather than in decompression, and invisible to 900,000 fuzz cases because the harness bounds output and a successful reservation produces none. The reservation is now clamped to the volume's size.
- **`ade ls --format=json … | head` no longer panics.** `println!` panics on a closed pipe, which for a tool built to be piped is unacceptable. All output now goes through an `emit` helper treating a closed pipe as the ordinary end of a command — `SIGPIPE` cannot be restored directly because that needs `unsafe`, which the workspace forbids.
- **The oracle test can no longer take down the host.** Its first run allocated 29 GB *inside `unadf`* on `Bomb Busters_Disk1.adf` and the kernel OOM killer terminated the session. Every invocation now runs under `ulimit -v` and `timeout`, applied via `sh` because `Command::pre_exec` needs `unsafe`, which the workspace forbids — the D-001 posture doing its job in a place I did not expect it.
- **BUG-001** (high) — `Dostype::is_international()` was the naive bit test and wrong for `DOS\4`/`DOS\5`, which are international with the INTL bit clear. Investigation found a second error the report had missed: `DOS\6`/`DOS\7` are the bit combinations the classic encoding left unused *because* dircache implies international, which is why LNFS claimed them — so they are dostypes, not bit patterns, and the old `has_dircache()` wrongly reported them as dircache volumes. Replaced bit predicates with a whole-byte `Mode` resolution. Verified against 4288 TOSEC images: 20 would have hashed wrongly before the fix.
- **BUG-002** (low) — `Geometry::midpoint()` used `total_blocks / 2`; renamed to `root_block()` and reimplemented as the documented `(numReserved + highKey) / 2` (ADF FAQ §4.2). `Geometry` carries `reserved`; `new()` takes it and rejects `reserved >= total_blocks`. Fixed ahead of its deferral because the API change was cheapest before anything depended on it.

- **D-010 Accepted** (Option E) — no disk image is committed to this repository in any form. Fixtures are generated in code at test time; `tests/fixtures/` holds a manifest and documentation only. Chosen over the earlier lean towards committed freely-distributable disks because a generator is reviewable where a binary is opaque, covers the three dostypes absent from the 4288-image corpus, and removes the copyright question entirely rather than managing it. The stated cost: CI never exercises a real disk, so the local corpus run must be habit.

- **`ade-fixtures`** — the D-010 fixture generator. Builds structurally valid Amiga volumes in code: any geometry including 81–83 cylinders, all eight dostypes, OFS and FFS data layout with the reversed `data_blocks[]` table, hash-table insertion with same-hash chaining, an accurate bitmap (set bit = free), and both checksum algorithms as separate functions so they cannot be confused. A `corrupt` module supplies the structures no genuine disk contains: AV-001 self-cycles and two-block cycles, AV-003 bitmap-flag invalidation, AV-004 out-of-range pointers, plus non-`DOS` bootblocks, truncation and trailing junk drawn from the survey. Depends on no other ADE crate — it states the format independently so a misreading in a layer crate cannot cancel out against it.
- **Corpus differential test** — the generator's checksum arithmetic checked against 3976 real `DOS` images: 3226 of 3229 well-typed rootblocks validate, and the bootblock rate reproduces the 74.1% measured independently in Python. Skips cleanly when `disks/` is absent, so a fresh clone passes offline.
- **`ade-fixtures --bin manifest`** — emits `sha256 size name` rows for a corpus directory, with a dependency-free SHA-256 verified against `sha256sum`.
- **`tests/fixtures/README.md`** — states the no-images policy, how to build fixtures, and that CI never exercises a real disk.

- **`ade info <image>`** — the first working command, and the first vertical slice through the pipeline. Reports the container kind *with the evidence behind it*, the bootblock, and the volume as three independent facts (C-008), then lists faults.
- **`ade-block::checksum`** — both algorithms as separately named functions (`normal`, `boot`) rather than one with a flag, because confusing them is a silent-corruption bug.
- **`ade-container`** — `RawImage` (an in-memory `BlockSource`) and `sniff`, an evidence cascade rather than a magic lookup. Handles the fact that plain ADF has no signature, that 81–83-cylinder images exist, and that a `DOS` prefix is neither necessary nor sufficient.
- **`ade-filesystem`** — `bootblock` and `rootblock` read-only inspection, plus `datestamp` decoding with a dependency-free civil-date conversion. Out-of-range datestamps are reported, never normalised: folding 90 minutes into an hour would destroy the evidence.
- **`ade-core::inspect`** — wires the layers; the single seam the CLI consumes.
- **CLI exit codes** (F-015): 0 clean, 1 faults, 2 usage, 3 unreadable, **4 no AmigaDOS volume**. 4 is separate deliberately — 1054 of 4288 real images have no rootblock where one should be, and reporting those as "clean" would mislead while calling them faulty would be wrong.
- Verified against the full corpus: 4288 images, **zero crashes**, container detection matching the independent census exactly. Findings included 248 stale bitmap-valid flags (AV-003 in the wild), 3 rootblock checksum failures and 3 dostypes carrying undocumented bits — each matching the earlier Python analysis.

- **Mount and traverse.** `ade-filesystem::volume::Volume` mounts from any `BlockSource`, lists directories through the hash table and its same-hash chains, resolves paths using the volume's own case folding, reads files through the reversed `data_blocks[]` table and extension blocks for both OFS and FFS, and walks the whole tree.
- **`ade-filesystem::entry`** — directory entries for every documented secondary type, including both hard-link forms and soft links, with protection flags whose owner bits are correctly inverted relative to group and other.
- **`ade-filesystem::hash`** — the directory hash and both case-folding variants, with a test that pins the `& 0x7ff` inside the loop rather than merely exercising the function.
- **`ade ls` and `ade extract`** commands.
- **AV-001 discharged in code.** Every chain walked carries a visited set of block numbers — hash chains, file extension chains, and the tree walk. A depth limit would not do: it cannot distinguish a legitimately deep tree from a two-block cycle. Tested against a self-loop, a two-block cycle, and a directory cycle of the kind a legitimate hard link produces.
- **`FileContents`** replaces a bare `Vec<u8>` from `read_file`, carrying the declared size and any shortfall, so a short read cannot pass unnoticed. ADE reports the gap rather than padding to the declared length: inventing bytes would be worse than admitting a gap.
- **IMP-001** logged — `ade ls` output is not machine-parseable, which F-015's "structured output" promise requires. Logged rather than fixed, per Maintenance Rule 8.

- **The D-002 oracle is live.** `unadf` and `xdms` installed; a differential test compares ADE's extraction against ADFlib byte-for-byte. Result over 80 disks: **2896 files compared, 2894 byte-identical (99.93%), zero unmatched paths.**
- **`Volume::entry_at` and `Volume::path_components`** — read the entry at a block, and walk the parent chain to a path. The walk carries a visited set, because a corrupt parent pointer loops as readily as a hash chain (AV-001).
- **D-012** — protection bits are metadata, not access control. Both oracle disagreements had one cause: ADFlib refuses to read files flagged unreadable and writes zero bytes; ADE recovers them. `Raffles.adf:s/startup-sequence` is flagged unreadable and yields 144 bytes of coherent AmigaDOS script. A 1989 permission bit is data about the disk, not an instruction to a preservation tool.

- **`--format=json`** on `ade info` and `ade ls` (IMP-001, F-015). `ls` emits JSON Lines so large directories stream; `info` emits one object with evidence and faults as arrays. Output is pure ASCII — Latin-1 names become `\uXXXX` escapes and round-trip losslessly, because a filename is bytes on a disk rather than text.
- **`ade_core::json`** — a small JSON writer, so the workspace keeps zero dependencies. ADE emits JSON and never parses it, so the whole escaping surface is one function.
- **`Inspection::faults()`** with a typed `Fault` carrying a **stable code** beside its message. Fault computation moved out of the CLI, so the human and JSON outputs cannot disagree about what is wrong with an image, and a future GUI inherits the same list.

- **Fuzz harness (F-001)** — six targets: block parsers, arbitrary-length inputs, the sniffer against mismatched declared sizes, mount-and-traverse, deliberately hostile structures, and truncated/extended images. Deterministic xorshift PRNG so any failure reproduces from its seed; structure-aware mutations (bit flips, field smashes, plausible-but-wrong block numbers) because a parser rejects pure noise at the first field. Hand-rolled rather than `cargo-fuzz`, which needs nightly while CI runs stable — a harness CI cannot run protects nothing against regressions.
- Unbounded *growth* is caught by structural bounds on outputs — a file cannot exceed its volume, a listing cannot exceed the block count — rather than by measuring the heap, since an allocator hook needs the `unsafe` the workspace forbids.
- CI runs the harness on every push. Deep sweeps are `ADE_FUZZ_ITERS=150000 cargo test --release --test fuzz`.
- **IMP-002** logged: OFS data blocks are read without validating `type`, `header_key` or `seq_num`, so garbage headers are silently treated as payload.
- **IMP-003** logged: `walk` and `read_file` are bounded only by their visited sets, with no second line of defence on the AV-001 invariant.

- **OFS data-block validation (IMP-002).** `read_file` checks each block's `type`, `header_key`, `seq_num` and `data_size` against what the table claimed, reporting mismatches through the new `FileContents::faults`. Nothing is refused — the bytes are read regardless (D-012) — but a file that stopped being a file part-way through now says so. Faults are summarised by kind rather than enumerated, coalescing on the discriminant so varied instances of one problem read as one finding.
- `FileContents::is_complete()` now means full-length **and** structurally sound; `is_full_length()` keeps the old meaning.
- `ade extract` reports structural faults on stderr, including when the byte count came out exactly right.
- New `corrupt` fixtures for each fault kind: wrong type, wrong owner, wrong sequence, oversized length, zeroed block.

- **IMP-003 applied** — `walk` returns a `Walk` carrying `hit_limit` and stops at three structural bounds independent of the visited set: entry count, pending directories, and **depth**. Depth was the one that mattered: bounding the count is not enough, because each path is built from its parent's, so a cycle grows the *strings* without bound while the count stays inside its cap.
- Verified by mutation: removing the visited set now yields a clean test failure in one second, naming the seed. The same mutation previously allocated 28.8 GB and the kernel killed the session.

- **`ade check` — the health report (F-010).** Gathers everything knowable about an image's condition in one pass and ranks it by severity: `info` for the cosmetic, `warning` for the odd, `error` for what would lose data. Findings carry stable codes; text and JSON output both available.
- **Bitmap cross-check (AV-003 detection).** `ade-filesystem::bitmap` reads the map — following the rootblock's 25 pointers and the `bm_ext` chain with a visited set, since extension blocks carry no checksum — and the health report compares it against the blocks the directory tree actually reaches. Two directions, two severities: *referenced but marked free* is an error, because the next write destroys live data; *marked used but unreachable* is a warning. Found on a real disk: block 25 of `Rolling Thunder.adf` is a live `T_DATA` block the bitmap says is free.
- **Cross-linked block detection** — a block reachable from two files, which writing either would corrupt.
- **`Volume::file_blocks`** — every block a file occupies, for bitmap cross-checking now and salvage later (F-012).
- **`Volume::geometry`** accessor; `checksum::normal_at` and `checksum::sums_to_zero`.
- **Exit code 5** for `check`: something would lose data. Distinct from 1 because "this disk is odd" and "do not write to this disk" are the two answers a batch run most needs separated.

- **D-010 amended**: the D-002 oracle validates *generated* fixtures, not only real images. ADFlib reads any structurally valid volume regardless of who wrote it, so the loop closes without a corpus — an independent implementation checks the generator as well as the parser, which is precisely the shared-misreading risk the entry was written to worry about. The boundary between the two mechanisms is not *generated versus real*; it is **conformance to the specification versus conformance to reality**.
- **`oracle_fixtures` test, running in CI.** ADFlib and ADE cross-checked on nine generated volumes — all eight dostypes plus a 1.76 MB HD volume, each carrying an accented filename so international hashing is exercised (C-006) — and byte-for-byte on multi-block file contents for both OFS and FFS. CI installs `unadf` and runs it on every push.
- The practical consequence: Phase 2's HD geometry, dostype matrix, LNFS and RDB work is properly verifiable, where it had looked fixture-only. The corpus contains none of those — no HD image, no `RDSK`, no `DOS\4`/`\6`/`\7`, no links in 8865 entries sampled.

- **Phase 2 opened: links and geometry.** Hard links resolve through `real_entry` — bounds-checked (AV-004) and with a visited set, since a looping pointer must terminate the walk not the process. `Volume::resolve` is a no-op on non-links so callers can resolve unconditionally; `read_file` resolves first; `walk` descends a directory link once rather than once per link pointing at it; `ade ls` shows `-> target`, or `BROKEN` with the reason.
- Soft links resolve to an error rather than a guess: they name a *path*, not a block, and AmigaDOS 3.0 removed support.
- **HD (1.76 MB) geometry** verified end to end for both OFS and FFS, with the rootblock computed at 1760 rather than read from the bootblock's misleading 880 (C-007). Extra-cylinder 81–83 geometries too.
- `Entry::next_link`; `FsError::BrokenLink`; `Volume::add_hardlink` in the fixture generator.
- **SPEC §Link block layout**, and the note that `unadf` omits link entries entirely — so link support is validated against the specification alone, with neither an independent implementation nor any corpus material. The one Phase 2 area where both of D-010's mechanisms come up empty.

- **Bitmap rebuild (AV-003, Phase 2).** `Bitmap::rebuild` computes the allocation map a volume should have from the blocks its tree reaches, returning the corrected block contents in memory. **Nothing is written**: D-004 defers write paths to Phase 4, and AV-003 asks for a rebuild to be offered. Correctness is proved by round-trip — build it, read it back, confirm it describes the set it was built from — plus repair of both damage directions and coverage of HD volumes.
- `Bitmap::orphaned` and `Bitmap::referenced_but_free` return the offending **block numbers**, and the health report names them: `Rolling Thunder.adf` now reads "1 blocks are in use by files but marked free (25)". Lists are summarised after six entries, since a report naming 1463 blocks individually is no more useful than one naming none.

- **Hardfiles mount (Phase 2).** `ade info`, `ls`, `extract` and `check` all work on an unpartitioned HDF. A raw volume has no geometry of its own — only the block count matters, since that fixes the rootblock — and ADFlib agrees, reporting an 8 MB hardfile as "Cylinders = 16384, Heads = 1, Sectors = 1". Added to the oracle test, which now cross-checks ten generated volumes.
- **IMP-004** logged: the fixture generator cannot build file extension blocks, so ADE's extension-chain reader is exercised only by real corpus disks — no fixture, and therefore no oracle.

- **IMP-004 applied: the fixture generator builds file extension blocks.** A file's header names 72 data blocks; anything larger chains the rest through extension blocks. ADE has read that chain since Phase 1 — it is how `taterm1` was recovered from a real disk — but nothing could generate one, so the path had no fixture, no test on a fresh clone, and **no oracle**. A 200 KB file now spans six extension blocks and ADFlib extracts it byte-identically to ADE, for OFS and FFS.
- With it, the AV-001 visited set guarding that chain is testable for the first time: `corrupt::extension_chain_loop` and `extension_chain_cycle` build a self-loop and a two-block cycle, and both terminate with a reported cycle. A "next != self" check would catch the first and miss the second.
- The oracle test now covers eleven generated volumes and four content round-trips.

### Changed
- **SPEC §Corpus observations** — new section recording a survey of 4288 TOSEC Amiga ADF images, explicitly labelled measurement rather than specification. Magic distribution, the 300 non-`DOS` images across 144 distinct bootloaders, bootblock-checksum and rootblock validity rates, and the non-canonical size distribution.
- **SPEC §Extended-ADF** — the `UAE-1ADF` layout, derived from eleven corpus images and verified arithmetically (`12 + tracks × 12 + Σ space` equals file size for all eleven). Track type 0 is standard sector data and 1 is raw MFM; `length` is in **bits**, `space` in bytes. Mixed types within one image are the copy-protection signature.
- **C-008** — new constraint: ADF identification is heuristic and must be reported as such. Neither magic, size, bootblock checksum, nor the `DOS` prefix is decisive, and each claim is now backed by a measured figure.
- **SPEC §Geometry** — 80 cylinders is the norm, not the limit; 81/82/83-cylinder images occur and land exactly on `cylinders × 2 × 11 × 512`.
- **D-010** — records that a 4288-image corpus now exists locally outside version control, settling the differential-testing half of the decision in practice; the committed-fixture half stays open.
- **AV-001 widened.** Directory cycles are reachable on structurally valid disks, because AmigaDOS permits hard links to directories. Cycle detection is a correctness requirement for ordinary images, not only a defence against hostile input, and must use a visited-set rather than a depth limit.
- **AV-003 corroborated** by the Linux AFFS documentation, which warns the bitmap-valid flag may be inaccurate after a crash — a routine condition, not only an attack. Noted also that a *set* bitmap bit means *free*, the opposite of the usual convention.
- **F-003** records the sniffing cascade: a plain ADF has no magic number, so content dispatch cannot be a magic lookup.
- Copyright holder in `LICENSE`, `NOTICE`, and workspace `authors` corrected from the bare handle to `Shane Hartley (Darian-Frey)`, so the notice names a legal person. Done before any external contribution, while it is still a one-party change. Recorded under D-011.
- **D-001 → Accepted** (Option A): Rust core exposing a C-ABI bridge, Qt6 GUI over it from Phase 5. The flux/IPF-binding half of the original reversal condition was withdrawn as unfounded.
- **D-002 → Accepted**, scope narrowed to ADFlib alone, decided as a new Option D: reimplement OFS/FFS/RDB in Rust with ADFlib as a **black-box differential-test oracle** — never linked, source never read. Rejects the previously-leaned hybrid, whose safety gap would have made F-001 unclaimable.
- **D-008** — deferral **discharged** and closed out: D-002 inherited no GPL obligation, and the resulting free choice was made the same day (see D-011). The entry stays in the register as the audit trail for the period without a licence.
- ARCHITECTURE, BUILD, SPEC, ROADMAP, FEATURES, ATTACK_VECTORS (AV-005), CLAUDE, and both READMEs updated for the settled stack. BUILD.md now distinguishes build dependencies from test-only ones; SPEC.md records that ADFlib's source is deliberately excluded from its reference list.

### Notes
- The workspace builds, tests (18 passing), lints clean, and documents without warnings. The engine is still a scaffold: no image is parsed yet, and `ade` has no commands.
- Next: the first vertical slice, `ade info <image>` — geometry, dostype, bootblock checksum — chosen over building layers bottom-up so that every seam is exercised before integration rather than after.
- `CLAIMS.md` omitted (non-research); `VOCABULARY.md` deferred (ManifeST contract undefined); `LICENSE` outstanding per D-008. Publication is gated on both `LICENSE` and D-010.

- **RDB multi-partition device support** (Phase 2, F-018 reading half). `ade-filesystem::rdb` parses `RDSK`, the `PART` chain and `FSHD`; `ade-container::Window` presents one partition as a volume. `ade info` reports the drive and its partition table, and `ls`, `extract` and `check` accept `--partition=` by drive name (case-insensitively, per C-006) or index. `Inspection` gains `rdb` and `partitions`; `Health` gains `examined`, naming the volume and partition a report actually covers — a device holds no volume at its own rootblock, so reporting "no volume" and exiting non-zero would have called a sound disk broken.
  - The RDB is **searched for** across the first 16 blocks rather than assumed at block 0, and the `PART` walk carries a visited set, so a cyclic or out-of-range chain is reported as a fault with the partitions found before it kept (AV-004).
  - `Window` re-validates every block number after translating it to the device, so a partition cannot be used to address outside itself — AV-004 holds across the boundary, not only within a volume. `ade-container` knows nothing of RDB; the partition extent is passed in, which keeps D-003 intact.
  - Two units the format makes easy to get wrong have dedicated tests: `SizeBlock` counts **longs** (128 for a 512-byte block), and RDB lists terminate at **-1**, not 0.
  - `ade info` no longer reports a bootblock for a device: block 0 is an `RDSK` structure, and parsing one there produced a confident report about a checksum that was never a checksum.
  - Cross-checked against ADFlib, which reads both partitions of a generated device at the same sector ranges ADE does (`oracle_fixtures.rs::adflib_reads_our_generated_device`).
- `tools/fixtures::device::Device` — builds RDB devices with a partition chain and a minimal `FSHD`/`LSEG` pair. `without_filesystem_driver()` builds the spec-legal shape ADFlib refuses, so that divergence stays visible.
- **SPEC §The oracle is stricter than the format here** — ADFlib will not mount a device without an `LSEG` chain, though FAQ §6.5 says one "isn't needed to reach partitions". Recorded, not resolved (D-012). Also records an ADFlib fill-percentage artefact on multi-block partition bitmaps, so it is not rediscovered as a suspected ADE bug.
- **SPEC §No corpus image carries an RDB** — the `RDSK` signature appears in the first 16 blocks of 0 of 4652 corpus images. The RDB path therefore has no corpus material and rests entirely on the D-002 oracle over generated devices, which is what D-010's amendment exists to permit.
- `ade-endian::i32_at` put to use for `BootPri`, which is signed — routing it through the C-001 seam rather than casting at the call site.

- **Directory cache blocks** (`DOS\4`, `DOS\5`) — Phase 2. `ade-filesystem::dircache` parses the chain hanging off a directory's `extension` field; `Volume::dircache` reads it and `Volume::has_dircache` says whether the volume keeps one. `Rootblock` gains a `dircache` field for the root's chain head.
  - **Fixed a live false positive.** Cache blocks are marked used in the bitmap, and nothing reached them, so the health report counted them as orphaned — 19 blocks on the Workbench 3.1 install disk, 14 on Subwar 2050. All 21 cached disks in the corpus now reconcile exactly, and 20 of them report no findings at all.
  - **The cross-check SPEC asks for.** A dircache duplicates the entry blocks, so `dircache::compare` reports where the two descriptions differ — by name, size, protection, comment, secondary type, or presence — and prefers neither, per SPEC §Directory cache blocks. `ade check` reports the comparison whether or not it finds anything: "compared and matched" is a different fact from "not checked". New finding codes `dircache-disagrees` and `dircache-chain-broken`; `Health` gains `dircache`.
  - Only real directories are searched for a cache. A hard link to a directory has an `extension` field too, and following it would walk whatever happens to be there.
  - Record lengths come off the disk, so both are bounded before use (name ≤ 30, comment ≤ 22) and a record that would run past the block ends the block rather than being invented. The chain carries a visited set (AV-001) and every block number is validated (AV-004). `dircache::parse` is now a fuzz target: 900,000 cases, no failures.
  - The secondary type is **one signed byte** here against the entry block's 32-bit word. `Record::secondary_type_widened` sign-extends, because comparing without it reports every file on the disk as a mismatch.
- `ade-fixtures` builds real dircache blocks for `DOS\4` and `DOS\5`, reading the records back out of the entry blocks that were actually written rather than from the generator's own bookkeeping — a cache assembled from that could agree with the generator while both disagreed with the disk.
- `corrupt::dircache_size`, `dircache_name`, `dircache_drop_last` and `dircache_chain_loop` — a stale cache is the one failure a dircache volume can suffer that no checksum catches, since both blocks still verify. Only the comparison finds it.
- **Oracle: `unadf -c`** lists a directory *from its cache* rather than by walking the hash chains, so it is the only external check that a cache ADE wrote is well-formed. It reads generated `DOS\4` and `DOS\5` volumes identically to their hash-chain listings.
- **SPEC §Confirmed against real disks** — the documented dircache layout verified across 1252 records in 133 blocks over the corpus's 21 cached disks, with zero disagreements. `DOS\4` is now covered by generated fixtures plus the oracle rather than being an open question.

- **SPEC §LNFS field-level pass** — discharges the open question of that name. The long-name entry block, `TYPE_COMMENT` block and root block are now documented at field level with byte offsets. [AOS-LNFS] declares them in C rather than as offset tables, so the offsets are the declaration order laid out; both structures sum to exactly 512 bytes and every field from 0x1F0 onward matches the classic layout, which is what makes the reading checkable rather than asserted.
  - Records the trap the two layouts create together: they share a primary type, a secondary type, a checksum algorithm and their whole tail, so **nothing in the block says which layout it is — only the volume's dostype does**. Read one as the other and the classic name field lands in LNFS's `Spare6` (empty names) while the classic datestamp lands inside `NaC` (name characters parsed as a date). Both blocks checksum correctly either way.
  - **SPEC §The file header is inferred, not documented** — [AOS-LNFS] declares no long-name file header at all. The three file-only fields are placed from the canonical file/directory block shape, which is sound reasoning but not a citation, and is recorded so a future failure is diagnosed rather than rediscovered.
- **SPEC §The oracle cannot check LNFS — it does not implement it.** ADFlib decodes the dostype by bit pattern, so `DOS\6` (`0b110`) and `DOS\7` (`0b111`) are reported as `OFS INTL DIRCACHE` and `FFS INTL DIRCACHE` — the exact trap C-006 and BUG-001 describe. `unadf -c` on a `DOS\7` volume then hunts for cache blocks LNFS never had, fails three checks, prints **an empty listing and exits 0**. Combined with LNFS's absence from the corpus, this leaves it the first structure in ADE with neither corpus material nor an oracle.
- `src/api/tests/dostype_lnfs.rs` — pins the ordering ADFlib got wrong. `Dostype::mode()` matches `6 | 7 => LongNames` *before* testing the dircache bit, so `has_dircache()` is false on LNFS and no cache is looked for. Nothing else can catch a regression here: there is no oracle and no corpus material, and the natural way to write that function is ADFlib's way.
- Corrected the dostype table's INTL column. Bold marks "international while the stored bit is clear", which is `DOS\4`/`DOS\5` only — `DOS\6`/`DOS\7` do carry the bit. The previous bolding implied otherwise and was misleading enough to produce a wrong test assertion before it was caught.
- **D-013** — new decision entry: LNFS is deferred on **verifiability, not effort**. The field-level pass is done and the layout is ready to implement; what is missing is any way to check the result. Identification and hashing stay (correct, corpus-independent, pinned by tests); the block structures are not implemented. One real `DOS\6`/`DOS\7` image, or an LNFS implementation in ADFlib, reverses it.
- `lnfs-unsupported` health finding. A classic read of a long-name block does not fail — it silently yields the wrong name, and still checksums, so nothing downstream notices. `ade check` now says the names are unreliable while block accounting and checksums are not affected. Delivered with D-013, because a silent wrong answer is the one outcome that decision must not produce.

- **SPEC §The wider dostype registry** — survey of Amiga filesystem identifiers beyond the AmigaDOS family, from [AMIGAWIKI], [DISKTYPE], [HYPERION-FS] and [AFFS], cross-checked against the corpus. Two conclusions: **`DOS\0`–`DOS\7` is complete** (no source consulted knows a `DOS\8` or `DOS\9`, so ADE's enumeration needs no ninth case), and the rest of the registry — muFS, PFS/PDS, SFS, AFS, CFS, JXFS, the AmigaOS 4 host-filesystem handlers, Unix and NetBSD types, swap, CD-ROM, `KICK`/`BOOU` — must be identified and declined rather than mounted. Records `SFS\1` as a beta that is format-incompatible with `SFS\2`, and `ID_VP255_DOS_DISK` ("FFS9") as an unresolved lead with no byte value found anywhere.
  - Measured: of 4652 corpus images, 4341 begin `DOS` and **not one** carries any other filesystem identifier. Foreign-dostype handling therefore has no corpus material; it matters chiefly on RDB devices, where `Partition::claims_amigados` is the guard.
  - The muFS open question is narrowed: the identifiers are now pinned, so what remains undecided is scope rather than identification.
- **SPEC §FDI is the licence-free flux format** — FDI (Vincent Joguin, 2000) stores raw low-level track data like IPF, but its specification is public and its tools are open source. C-003 gates IPF behind a licence and forbids ADE from emitting it, so FDI is worth considering as a Phase 4 interchange target alongside SCP (D-007). Not scheduled; recorded so the option is visible when Phase 4 is planned rather than discovered afterwards. Its magic bytes are asserted, not verified.
- **Fixed: a bootblock was reported for containers that have none.** An extended ADF opens with `UAE-1ADF`, so `ade info` was reporting a dostype of `0x5541452d` and "checksum invalid" for a checksum that was never one — the same defect fixed earlier for RDB devices, found by auditing the corpus's 11 extended ADFs during this survey. `Kind::has_bootblock` now decides, and the report says "none — extended ADF has no bootblock at block 0" rather than staying silent. `Unknown` deliberately keeps its bootblock report: 7% of real images have a non-`DOS` bootblock and some still mount (C-008).
- Corpus note: three images (`Shadowlands_Disk2`, `Shadoworlds_Disk2`, `F.1 Manager_Disk2`) carry a bootblock reading `DOS2` in ASCII — dostype byte `0x32`, not a flags value. ADE reports it as `DOS\50 (OFS, INTL, unknown bits 0x30)` with a `dostype-unknown-bits` fault and finds no rootblock, which is the correct outcome: the bits are preserved and reported rather than guessed at.

- **ADZ and HDZ — gzip-wrapped images** (Phase 3, F-003). `ade-container::inflate` implements DEFLATE (RFC 1951) and the gzip wrapper (RFC 1952) from the specifications; the workspace has no dependencies, so there was nothing to reach for. An ADZ now inspects, mounts, lists, extracts and health-checks exactly as the ADF inside it.
  - The container reported is the **inner** one — what the user has is an Amiga floppy, and gzip is how it was stored — with the wrapper reported alongside it rather than hidden: `compressed  gzip, 245130 bytes on disk -> 901120 bytes`. `Inspection` gains `compression`.
  - **The oracle here is stronger than D-002's.** The system `gzip` compresses, ADE decompresses, and the result is either byte-identical or wrong — there is no interpretive gap to adjudicate. A deterministic sample of real corpus images round-trips byte-for-byte, and a damaged stream either errors or reproduces the original exactly, never something in between.
  - **AV-005 is discharged for this path.** The output cap is checked before every write, never after: a 970 KB stream expanding to 1 GB is refused at a peak RSS of 515 MB against the 512 MiB cap, rather than being decompressed and then complained about. Nothing is sized from a declared length — gzip's `ISIZE` is *verified* after the fact, never trusted before it, which is BUG-003's lesson applied where the attacker holds the pen. A back-reference before the start of the output is an error, which is AV-004's equivalent inside the decompressor.
  - `inflate::parse` and `gunzip` are fuzz targets, with a deliberately small cap so a runaway case is caught by an assertion rather than the OOM killer.
  - `examine` unwraps for itself: it reads blocks directly rather than through the inspection, and passing it the still-compressed bytes reported a truncated image on a sound disk.
- **SPEC §ADZ and HDZ (gzip)**, **§Decompression is the AV-005 surface**, **§The oracle for gzip is stronger than the one for ADF** — the header layout, the three rules the inflater is built around, and why gzip's little-endian framing is a deliberate exception to C-001 (which governs *disk* data).
- Two test bugs worth recording, both of which passed on small inputs and failed on real ones: a `gzip` helper that wrote to a child's stdin while nothing drained its stdout **deadlocked** once the compressed output exceeded the pipe buffer, and an "incompressible" test vector built from a weak mixer compressed 22:1 — so the stored-block path it was meant to cover was never exercised. Both now assert the property they depend on.

- **Bootblock banner extraction** (Phase 3, F-011). `Bootblock::text` pulls printable runs from the boot code, filtered so what is reported is prose rather than 68k opcodes — `NqNqNq` is three `NOP`s (0x4E71), and an unfiltered extractor reports mostly padding. `ade info` shows it, `Inspection` gains `boot_text`, and the JSON carries offsets alongside the text.
  - The filters are measured, not guessed: a 10-character floor, rejection of any run that is one unit of ≤ 4 bytes repeated, an 85% "looks like prose" threshold, and dropping `.library`/`.device`/`.resource` names that every bootblock carries. Across the corpus that leaves ~20% of disks with reportable text and **91% of kept runs containing a space** — the measure used to separate prose from code.
  - BCPL-style length prefixes are stripped **exactly**, not heuristically: the leading byte goes only when its value is precisely the length of what follows. `'` is 0x27 = 39, and the message after it in the corpus is 39 characters.
  - What it finds is catalogue material as much as security: `Copylock Amiga (c)1988-91 Rob Northen Computing`, `SKID ROW 1991`, `Cracked by Eagle Soft!`, `Doppleganger's OVERSEER Virus Protector v1.0`.
- **D-014** — new decision entry: bootblock **virus identification is deferred**, and the reason is measured rather than assumed. No checkable signature set is published (the established brainfile CRCs ship as opaque binaries), and matching strain names is **inverted**: all 107 corpus disks that name a virus carry *anti-virus* bootblocks — `CANNOT BE INFECTED BY THE SCA-VIRUS`, `PROTECT AGAINST: BYTEWARRIOR, LAMER Extermin.`, and one virus killer whose menu lists nine strains. Cracking groups installed virus killers routinely, so a name-matcher would flag precisely the disks that were cleaned. ADE reports what the bootblock says and draws no conclusion.
- **AV-002's primary defence recorded as structural.** The vector is *executing* guest boot code; ADE has no interpreter, no emulator and no execution path of any kind. `boot_text.rs` pins this with boot code written to be hostile to a reader — `BRA` to self, `TRAP #0`, all-ones and all-zeros — so the property holds by intent rather than by accident.

- **Format-conversion matrix** (Phase 3, F-016). `ade-core::convert` gives every pair of container formats an explicit answer carrying its own reason — lossless, lossy and what is lost, not implemented and why, or refused and why. `ade formats` prints the matrix; `ade convert <in> <out>` obeys it.
  - **Refused and not-implemented are kept distinct**, because they invite opposite follow-up. IPF output is a licence decision that does not expire (C-003); DMS input is a gap waiting on material (D-009); flux writing waits on Phase 4 (D-005). Reporting them alike would tell someone to wait for something that is never coming.
  - **Lossy conversions are refused outright, not warned about.** Flattening an extended ADF or an SCP capture to sectors discards the copy protection that was the reason to capture it, the loss is not recoverable, and a warning nobody reads is how it happens. No flag enables it.
  - Conversions that run: the decompression direction, whose reader is proven byte-identically against real images — which is exactly what D-004 requires before a write path ships — and copies between sector containers, which differ only by naming convention (SPEC §A raw volume has no geometry).
  - **An existing output is never overwritten.** A conversion that replaces a file is the irreversible damage D-004 is about, and a source image is what someone points this at by accident.
  - The output format is taken from the extension because the file does not exist yet; **inputs are always identified by content**, keeping C-008's habit of trusting evidence over labels.
- **SPEC §Conversion is mostly a question about loss** — why the matrix exists: sector containers are interchangeable byte-for-byte, flux containers are not, and flattening one is a discard that produces a perfectly valid ADF with no record that anything went missing.

- **`FILE_ID.DIZ` surfacing** (Phase 3, F-011). `ade info` reads the disk's own description and prints it; `Inspection` gains `description`, and the JSON carries the text, the stored filename, the block and whether it was truncated.
  - Rare — 0.6% of a 500-disk sample — but disproportionately informative, because it says what the volume name often does not. One corpus disk is labelled `Empty`; its description reads `TEST MATCH CRiCKET SAVE DISK (NEEDED) [2/2]`.
  - Found **case-insensitively**: `file_id.diz`, `FILE_ID.DIZ` and `File_ID.Diz` all occur on real disks, and AmigaDOS filenames are not case sensitive (C-006). The name is reported **as stored**, since what is on the disk is a fact about the disk.
  - Read from the root directory only — the BBS convention puts it there, and searching a whole disk by name is a different feature with a different cost — and capped at 8 KB, because the length comes off the disk (AV-005, BUG-003). The declared size is still reported in full: the cap is on what is read, not on what is claimed.
  - Decoded as Latin-1, so the high-bit box-drawing characters that make up release art survive rather than being mangled as UTF-8. A directory of that name is ignored rather than read as text.

- **Extended-ADF reading** (Phase 4 begins, F-003). `ade-container::extended` parses the `UAE-1ADF` track table; `ade info` reports how many tracks hold ordinary sectors, how many hold raw MFM, and how many hold nothing. `Inspection` gains `tracks`.
  - **`space` is the file allocation; `length` is the meaningful extent.** Measured across all 428 type-0 tracks in the corpus: `length` is 45056 bits in every one — 5632 bytes, one standard DD track — while `space` is 5632, 12650 or 12668 depending on the writer. Reading `space` bytes as sectors would take up to seven kilobytes of padding as data.
  - **A track may hold nothing.** 154 observed type-1 tracks have `space` and `length` both zero: unformatted or never captured, which is a fact about the disk rather than damage to the file.
  - **Damage is a fault, not a failure.** `Demolition.adf` is genuinely 25,732 bytes short, ending inside track 163 of a declared 166; it now yields 163 tracks and a precise report rather than nothing.
  - A wild track count is refused before allocating a table from it (AV-005), and an unknown track type is reported rather than guessed.
- **SPEC §Extended-ADF corrected.** It claimed `12 + tracks × 12 + Σ space` equals the file size "for all eleven" corpus images. It holds for ten — `Demolition.adf` fails it. The arithmetic is the right check, and is what found the truncation, but it is a test a file can fail rather than an invariant. The section also said "a type-0 track reads `space = 5632`", true of only one writer in three.
- **SPEC §The sector tracks really are sectors** — assembling the type-0 tracks of an extended ADF into a plain ADF produces a mountable volume where enough of the disk is ordinary (`Demolition`, `REALM OF THE TROLLS`). This is what confirms the layout rather than merely fitting it: arithmetic can be satisfied by a wrong reading; a legible rootblock at block 880 cannot. It also shows what a type mix means — `Champ, The` is 159 of 160 ordinary tracks, with the one raw track exactly where the rootblock would be.

- **MFM track decoding** (Phase 4, D-005's track model populated). `ade-track` decodes raw tracks into Amiga sectors — sync search, the odd/even split, the sector header, and both checksums. `ade info` reports how much of a raw-track disk is ordinary and how much is protection.
  - **The decode is self-evidencing**, which is a stronger position than anything else in this project. Every sector carries two checksums of its own, so no oracle is needed: **2095 sectors across the corpus's 1235 raw tracks decode with both agreeing**. Confirmed a second way — `Superman - The Man of Steel_Disk2` track 80 decodes as ten sectors that all say track 80, matching their physical position.
  - **The odd/even half order was decided by evidence, not by choosing a source.** Descriptions disagree; both orders were tried against a real track and only one produced matching checksums (odd first). The wrong choice does not fail loudly — it yields plausible bytes and a silently wrong disk.
  - **A track is a bit stream.** Sectors do not begin on byte boundaries: in one `Realm of the Trolls` track every sync sits at bit offset ≡ 7 (mod 8). The first implementation scanned byte-aligned, decoded 8% of the corpus's sectors, and looked like a disappointing disk rather than a broken reader.
  - **A sync mark is not a sector mark.** Three sync words occur throughout the corpus where two is the norm, and miscounting lands in the gap — which decodes to a header claiming format `0xAA` and track 168. More importantly a sync need not have a sector behind it at all: that is how a custom loader finds its own data. Gap decodes to all zeros and **zero satisfies its own checksum**, so a checksum test cannot tell gap from sector; the `0xFF` format byte is the only reliable marker.
  - What this buys, per disk: `Terrorpods` is 95 of 96 raw tracks fully standard — captured raw but not protected. `Wings of Death_DiskB` is 0 of 160, with 6144 sync marks leading nowhere. That difference is now visible rather than inferred.
- **SPEC §MFM** — the sector layout at byte level, the checksum definition, the odd/even formula, and the three traps above, each with the corpus measurement behind it. Closes the "MFM track and sector framing" open question; [RKRM] Appendix C was not needed. **§What this decoder does not check** records the honest limit: clock bits are masked off rather than verified, so MFM encoding violations — a real protection technique — cannot currently be detected.
- Two disks (`Deep Space`, `Terrorpods`) have every raw track claiming to be **track 0**, with checksums fully valid. That is a property of those disks rather than a decoding error, and it is why reconstructing an ADF by physical track position fails on them.

- **Clock-bit verification** (Phase 4). `ade-track::clock_violations` checks the MFM encoding rule itself — a clock bit is set only when the previous and current data bits are both zero — rather than masking clock bits off as the decoder does. `Sector` gains `clock_violations` and `clock_valid()`; `TrackDecode` gains `sync_words` and `clock_violations`.
  - Confirmed exactly on a real sector: **0 of 4095 data clock bits wrong, 0 of 1279 header ones, and 2 wrong in the two sync words**. That last is the point — `0x4489` is deliberately illegal MFM, one violation per sync word, which is precisely what makes it findable where ordinary data cannot produce it.
  - **The clock/data phase is only knowable from a sync word**, since a track's byte boundaries say nothing about where its bit pairs begin. A track with no sync reports `None` rather than guessing a phase and deriving a count from it.
  - Measured: **every one of the corpus's 2095 sound sectors is legally encoded.** There is no illegal MFM inside sectors in this material — these disks protect themselves structurally, with sync marks in the gaps and non-standard layouts, rather than by encoding bytes a drive could not write.
- **A negative result, recorded rather than shipped.** Subtracting the sync-word count from a track's total violations looked like an illegal-MFM protection indicator. It was implemented, measured, and **abandoned**: a sync word does not contribute exactly one violation, because the transitions into and out of a sync region contribute their own — a known-good Terrorpods track has 22 sync words and 27 violations. Counting the baseline two different ways produced two contradictory pictures of which disks were protected, the first making the *most* heavily protected ones look cleanest. ADE reports the raw counts, which are facts, and derives no score from their difference. SPEC §A violation count is not a protection score records why, so it is not reinvented.

- **Raw-track + filesystem dual view** (Phase 4, F-007). `ade-core::assemble` reconstructs a plain image from whatever a raw-track container yields — ordinary tracks as they are, raw tracks MFM-decoded — so an extended ADF is reported *both* as a track table, which is what it is, and as a volume, which is what most of it holds.
  - **Six of the corpus's eleven extended ADFs now mount**, and their content was previously unreachable by any part of ADE: `Demolition` gives 29 files and 560 KB, `REALM OF THE TROLLS` 8 files and 372 KB, `BDC A` and two disks whose volume is named `protec`. `ls`, `extract` and `check` all read through the reconstruction.
  - **Sectors are placed by physical position**, not by the track number they claim. `Deep Space` and `Terrorpods` label every raw track as track 0, so trusting that field would pile a whole disk onto track 0 — which is also why those two assemble to nothing usable despite decoding over a thousand sectors each.
  - **It is a reconstruction and says so, everywhere it is shown.** Undecodable sectors read as zeros, so a listing can silently omit half a disk. `ade info` reports `880 of 1760 sectors (50% of a disk)` before the volume, and `ade check` adds a `volume-reconstructed` finding — because "880 orphaned blocks" means something quite different on a disk half of which was never recovered, and the existing message ("lost space, or deleted files") would have been wrong in both halves.
  - A container with nothing readable reports no volume rather than an empty one: an image of pure protection has no filesystem view to offer, and inventing one is worse than saying so.
  - `examine` inspects the **original** bytes and reads blocks from the reconstruction. Inspecting the assembled bytes reported a protected disk's container as a plain ADF.

- **MFM encoding and extended-ADF writing** (Phase 4). `ade-track::encode_sector`/`encode_track` are the inverse of the decoder, and `ade-container::extended::write` emits the container. `ade convert --raw in.adf out.adf` writes a sector image as raw MFM tracks.
  - **Verified by round-trip, which is what D-004's ordering buys.** The read path was proven first — 2095 corpus sectors decoding with both of their own checksums agreeing — so the decoder is a trustworthy judge of the encoder. A whole disk encoded track by track, written, read back, decoded and reassembled comes out **byte-identical** and mounts under its own name: 1760 of 1760 sectors, 160 of 160 tracks standard, 0 stray syncs.
  - **Clock bits are computed, not left clear.** This is the part a test helper can skip and a real encoder cannot: a clock bit depends on the data bit before it, so the body is written as one continuous stream and the clock pass runs over the whole of it. The sync words are excluded deliberately — their illegality is what makes them findable.
  - A sector is emitted at the documented **1088 bytes**: four of lead-in, four of sync, 1080 of body. An earlier version put the lead-in in the gap and emitted 1084, which read back correctly but did not match SPEC.
  - `--raw` is a flag rather than an output extension, because an extended ADF is also called `.adf`. The format has no distinct extension and inventing one would be presumptuous.
  - The conversion matrix records sector image → raw MFM as **lossless**, which it provably is. The reverse stays lossy: flattening an extended ADF discards raw tracks that *could* hold protection, and the matrix is conservative about that even when they happen not to.
- An independent confirmation of the earlier negative result: this encoder produces a perfectly-formed track with **22 sync words and 28 clock violations**, matching the 22-and-27 measured on a real Terrorpods track. Sync *boundaries* contribute violations of their own, which is exactly why "violations minus sync words" is not a protection score (SPEC §A violation count is not a protection score).

- **Consolidation and diffing** (Phase 4, F-008 and F-009). `ade-core::consolidate` merges several dumps of one disk sector by sector and reports where they disagree; `ade-core::diff` locates the differences between two. `ade consolidate a.adf b.adf ...` and `ade diff a.adf b.adf` expose both. Consolidation is **report-only by default** — writing a merged image needs `--output=`, and never overwrites an existing file.
  - **A correction: this was previously recorded as blocked on material, and that was wrong.** The corpus holds **46 titles whose dumps genuinely differ**, several with six versions. Six dumps of Workbench v1.0 give 1400 sectors agreed, 348 resolved by plurality and 12 tied.
  - **It reports agreement, not correctness.** F-008's wording — "merge N reads of the same disk into a best-estimate image" — assumes the reads came from one physical disk, so a disagreement means a read failed. The available material is not that: these are independent dumps of possibly different copies, and several are TOSEC-tagged `[m files moved]` or `[m startup-sequence]`, i.e. deliberate edits. One corpus pair differs in exactly one sector — block 880, the rootblock, by 17 bytes, which is a volume datestamp. Neither dump is wrong. So the tool names the disputed tracks and how the votes fell, and declines to pronounce a winner correct; the CLI says so in as many words.
  - **Two dumps cannot vote.** With two sources every disagreement is a tie by definition, and the report states that rather than presenting arithmetic as judgement.
  - Merging is **per sector**, reporting **per track**. Differences are often confined to one sector, so merging whole tracks on a plurality would discard good sectors along with the disputed one; F-008 asks for a per-track report and that is what is given.

- **Corpus-scale batch operations** (Phase 5, F-014). `ade batch <dir|image>...` verifies a whole corpus in one pass and reports a histogram — containers, findings, how many mounted, how many are sound, bytes recovered — in text or JSON. Records stream as JSON Lines followed by a summary object; progress goes to **stderr** so stdout stays clean when piped.
  - **The full 4652-image corpus runs in 5.5 seconds at 9 MB peak RSS.** One image is read, examined and dropped, so memory does not scale with the corpus. 3601 mount (77%), 2847 are sound (61%), none is unreadable, and 2.2 GB of file content is recovered. This is the capability every corpus measurement in SPEC was taken by hand-rolling a script for.
  - **Nothing aborts a run.** An unreadable image becomes a record rather than an error: a pass over four thousand disks that stops at the first bad one has reported on one disk. Results are in sorted path order, so two runs are comparable and a failure is reproducible.
- **Fixed: `bitmap-flag-clear` was reported twice.** It was raised both as an `Inspection` fault and again by the health report's bitmap cross-check, so `ade check` listed the same warning twice in slightly different words. **Found by the batch histogram** — the code appeared on exactly twice as many images as carried it, which is the sort of pattern only a corpus-scale view makes visible.
- **Fixed, in the batch report itself: findings are counted once per image, not once per occurrence.** A damaged disk can raise `data-block-structure` dozens of times; summing those made **186 affected images read as 1050**. Caught by cross-checking two suspiciously equal totals in the feature's own first run over the corpus.

- **SCP is no longer blocked on material** (Phase 4, D-007) — a reversal of an earlier judgement, recorded here because the judgement was wrong rather than merely outdated. The Greaseweazle host tools (`gw`) convert a plain sector image into real SCP, so every one of the 4652 corpus ADFs is potential material; and because `gw` is an independent implementation, it is an **oracle** in exactly the sense D-002 and D-010 mean. Verified: five varied disks round-trip ADF → SCP → ADF **byte-identically**, HFE does too, and ADE's sniffer already identifies a generated SCP as `SCP flux`.
  - **Generation is not deterministic.** Converting one ADF twice yields two different SCP files — flux timings carry jitter, which is the point of the format. An SCP fixture therefore cannot be committed and compared byte for byte; it must be generated at test time, with the **round trip** as the invariant. That suits D-010, which commits no binaries anyway.
  - **`gw` does not understand extended ADF**, and fails silently. Given a 2,004,560-byte `UAE-1ADF` container it read the first 901,120 bytes of the *file* as sectors — header included — and reported "Found 1760 sectors of 1760 (100%)". The round trip is self-consistent and the input reading is nonsense. It is an oracle for plain sector images only; pointed at a raw-track container it agrees with itself about the wrong data.
  - C-003 gains independent corroboration: `gw` writes SCP and HFE but refuses IPF as an output format.

- **Auto-identification against TOSEC** (Phase 5, F-013). `ade-catalogue` parses Logiqx XML datfiles and indexes them by CRC32; `ade identify --datfiles=DIR <image>...` names images by content, and `ade batch --datfiles=DIR` catalogues a whole corpus in one pass.
  - **4586 of 4652 corpus images identified (98%)** from 88,921 entries across 98 Amiga datfiles. What it recovers is what a renamed file has lost: `1000cc Turbo.adf` becomes `1000cc Turbo (1990)(Energize)[cr CSL][t +3 Supplex]`, and `Karate Master.adf` becomes `Karate Master (1994)(Maddison, Rob - F1 Licenceware)(LW)[h Nemesis][AMOS]`.
  - **CRC32 is a content hash, not an identity.** Measured before designing around it: **71 collisions among 88,833 entries**, and size does not separate them — the colliding pairs share a length. None involves an `.adf`, and no corpus image lands on one, so the risk is theoretical today rather than absent. `identify` therefore returns **every** match and reports when there is more than one, rather than choosing.
  - A scanner rather than an XML parser, since ADE has no dependencies and the shape is narrow. Attributes are read **by name**, so attribute order cannot break it, and the five XML entities are resolved — only `&amp;` occurs, 8772 times.
  - Cost over the corpus: 13 seconds and 76 MB, against 5.5 seconds and 9 MB without. The dataset load is **0.17s** of that; the remainder is CRC32 over 4.2 GB of image data, which is inherent.
- **CRC32 moved from `ade-container::inflate` to `ade-block::checksum`**, with a re-export left where gzip callers expect it. Two unrelated parts of ADE need the same algorithm — gzip verifies a decompressed image with it, TOSEC identifies one — and implementing a checksum twice is how two copies of it silently diverge. `ade-block` is the lowest layer both can reach.
- **Layering policy amended** so `ade-catalogue` may depend on `ade-block`. A deliberate edit to `tools/check-layering.py`, which is what that file exists for: the point of the policy is to make a cross-layer edge visible in review rather than impossible.
