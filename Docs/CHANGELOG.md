### Fixed
- **BUG-006 (medium)** — the fixture generator wrote exactly one bitmap block and panicked on any volume above about 2 MB, where a second is needed. An 8 MB hardfile needs five. Every fixture until now was a floppy, comfortably inside one block, so the limit only appeared when Phase 2 asked for a volume large enough to matter. `write_bitmap` now allocates as many as the geometry needs and fills the rootblock's `bm_pages`.
- **BUG-005 (high)** — reading a hard link returned `Ok("")`, an empty file, silently. A link block holds no data; `real_entry` names the block it stands for, and that field was parsed but never used. Found on the first Phase 2 task by checking what the existing code already did with a link, rather than by a test — the corpus has no links and the generator could not build one.
- **CI toolchain drift.** `rust-toolchain.toml` said `channel = "stable"`, so CI installed whatever the runner had (1.98.0) while local development sat on 1.94.1 — four releases apart. With `-D warnings`, a lint added in any of those releases breaks the build with no code change, which is exactly what happened: `unnecessary_sort_by`, new in 1.98, rejected a reverse sort that passed locally. The toolchain is now pinned to an exact version, and a non-blocking `toolchain-drift` job lints against latest stable so falling behind surfaces as a warning rather than a red build.
- **BUG-004 (medium)** — the fixture generator wrote the bitmap checksum at offset 20, where every *other* block type keeps it, overwriting the map words covering blocks 130–161. Bitmap blocks are the one exception: checksum at 0, map from 4. It hid because the normal checksum makes the whole block sum to zero, so validation passes wherever the field sits; only the layout differs. Surfaced by fixtures reporting 27 orphaned blocks where real disks reported none — D-010's two mechanisms catching the *generator* rather than the parser, which is the direction I had not anticipated.
- **BUG-003 (high)** — `read_file` reserved `Vec::with_capacity(byte_size)` from a `u32` read straight off the disk, so a crafted header made ADE attempt a 4 GB allocation on an 880 KB floppy before reading anything. AV-005 in one line, on the plain ADF path rather than in decompression, and invisible to 900,000 fuzz cases because the harness bounds output and a successful reservation produces none. The reservation is now clamped to the volume's size.
- **`ade ls --format=json … | head` no longer panics.** `println!` panics on a closed pipe, which for a tool built to be piped is unacceptable. All output now goes through an `emit` helper treating a closed pipe as the ordinary end of a command — `SIGPIPE` cannot be restored directly because that needs `unsafe`, which the workspace forbids.
- **The oracle test can no longer take down the host.** Its first run allocated 29 GB *inside `unadf`* on `Bomb Busters_Disk1.adf` and the kernel OOM killer terminated the session. Every invocation now runs under `ulimit -v` and `timeout`, applied via `sh` because `Command::pre_exec` needs `unsafe`, which the workspace forbids — the D-001 posture doing its job in a place I did not expect it.
- **BUG-001** (high) — `Dostype::is_international()` was the naive bit test and wrong for `DOS\4`/`DOS\5`, which are international with the INTL bit clear. Investigation found a second error the report had missed: `DOS\6`/`DOS\7` are the bit combinations the classic encoding left unused *because* dircache implies international, which is why LNFS claimed them — so they are dostypes, not bit patterns, and the old `has_dircache()` wrongly reported them as dircache volumes. Replaced bit predicates with a whole-byte `Mode` resolution. Verified against 4288 TOSEC images: 20 would have hashed wrongly before the fix.
- **BUG-002** (low) — `Geometry::midpoint()` used `total_blocks / 2`; renamed to `root_block()` and reimplemented as the documented `(numReserved + highKey) / 2` (ADF FAQ §4.2). `Geometry` carries `reserved`; `new()` takes it and rejects `reserved >= total_blocks`. Fixed ahead of its deferral because the API change was cheapest before anything depended on it.

- **D-010 Accepted** (Option E) — no disk image is committed to this repository in any form. Fixtures are generated in code at test time; `tests/fixtures/` holds a manifest and documentation only. Chosen over the earlier lean towards committed freely-distributable disks because a generator is reviewable where a binary is opaque, covers the three dostypes absent from the 4288-image corpus, and removes the copyright question entirely rather than managing it. The stated cost: CI never exercises a real disk, so the local corpus run must be habit.

- **`ade-fixtures`** — the D-010 fixture generator. Builds structurally valid Amiga volumes in code: any geometry including 81–83 cylinders, all eight dostypes, OFS and FFS data layout with the reversed `data_blocks[]` table, hash-table insertion with same-hash chaining, an accurate bitmap (set bit = free), and both checksum algorithms as separate functions so they cannot be confused. A `corrupt` module supplies the structures no genuine disk contains: AV-001 self-cycles and two-block cycles, AV-003 bitmap-flag invalidation, AV-004 out-of-range pointers, plus non-`DOS` bootblocks, truncation and trailing junk drawn from the survey. Depends on no other ADE crate — it states the format independently so a misreading in a layer crate cannot cancel out against it.
- **Corpus differential test** — the generator's checksum arithmetic checked against 3976 real `DOS` images: 3226 of 3229 well-typed rootblocks validate, and the bootblock rate reproduces the 74.1% measured independently in Python. Skips cleanly when `disks/` is absent, so a fresh clone passes offline.
- **`ade-fixtures --bin manifest`** — emits `sha256 size name` rows for a corpus directory, with a dependency-free SHA-256 verified against `sha256sum`.
- **`tests/fixtures/README.md`** — states the no-images policy, how to build fixtures, and that CI never exercises a real disk.

- **`ade info <image>`** — the first working command, and the first vertical slice through the pipeline. Reports the container kind *with the evidence behind it*, the bootblock, and the volume as three independent facts (C-008), then lists faults.
- **`ade-block::checksum`** — both algorithms as separately named functions (`normal`, `boot`) rather than one with a flag, because confusing them is a silent-corruption bug.
- **`ade-container`** — `RawImage` (an in-memory `BlockSource`) and `sniff`, an evidence cascade rather than a magic lookup. Handles the fact that plain ADF has no signature, that 81–83-cylinder images exist, and that a `DOS` prefix is neither necessary nor sufficient.
- **`ade-filesystem`** — `bootblock` and `rootblock` read-only inspection, plus `datestamp` decoding with a dependency-free civil-date conversion. Out-of-range datestamps are reported, never normalised: folding 90 minutes into an hour would destroy the evidence.
- **`ade-core::inspect`** — wires the layers; the single seam the CLI consumes.
- **CLI exit codes** (F-015): 0 clean, 1 faults, 2 usage, 3 unreadable, **4 no AmigaDOS volume**. 4 is separate deliberately — 1054 of 4288 real images have no rootblock where one should be, and reporting those as "clean" would mislead while calling them faulty would be wrong.
- Verified against the full corpus: 4288 images, **zero crashes**, container detection matching the independent census exactly. Findings included 248 stale bitmap-valid flags (AV-003 in the wild), 3 rootblock checksum failures and 3 dostypes carrying undocumented bits — each matching the earlier Python analysis.

- **Mount and traverse.** `ade-filesystem::volume::Volume` mounts from any `BlockSource`, lists directories through the hash table and its same-hash chains, resolves paths using the volume's own case folding, reads files through the reversed `data_blocks[]` table and extension blocks for both OFS and FFS, and walks the whole tree.
- **`ade-filesystem::entry`** — directory entries for every documented secondary type, including both hard-link forms and soft links, with protection flags whose owner bits are correctly inverted relative to group and other.
- **`ade-filesystem::hash`** — the directory hash and both case-folding variants, with a test that pins the `& 0x7ff` inside the loop rather than merely exercising the function.
- **`ade ls` and `ade extract`** commands.
- **AV-001 discharged in code.** Every chain walked carries a visited set of block numbers — hash chains, file extension chains, and the tree walk. A depth limit would not do: it cannot distinguish a legitimately deep tree from a two-block cycle. Tested against a self-loop, a two-block cycle, and a directory cycle of the kind a legitimate hard link produces.
- **`FileContents`** replaces a bare `Vec<u8>` from `read_file`, carrying the declared size and any shortfall, so a short read cannot pass unnoticed. ADE reports the gap rather than padding to the declared length: inventing bytes would be worse than admitting a gap.
- **IMP-001** logged — `ade ls` output is not machine-parseable, which F-015's "structured output" promise requires. Logged rather than fixed, per Maintenance Rule 8.

- **The D-002 oracle is live.** `unadf` and `xdms` installed; a differential test compares ADE's extraction against ADFlib byte-for-byte. Result over 80 disks: **2896 files compared, 2894 byte-identical (99.93%), zero unmatched paths.**
- **`Volume::entry_at` and `Volume::path_components`** — read the entry at a block, and walk the parent chain to a path. The walk carries a visited set, because a corrupt parent pointer loops as readily as a hash chain (AV-001).
- **D-012** — protection bits are metadata, not access control. Both oracle disagreements had one cause: ADFlib refuses to read files flagged unreadable and writes zero bytes; ADE recovers them. `Raffles.adf:s/startup-sequence` is flagged unreadable and yields 144 bytes of coherent AmigaDOS script. A 1989 permission bit is data about the disk, not an instruction to a preservation tool.

- **`--format=json`** on `ade info` and `ade ls` (IMP-001, F-015). `ls` emits JSON Lines so large directories stream; `info` emits one object with evidence and faults as arrays. Output is pure ASCII — Latin-1 names become `\uXXXX` escapes and round-trip losslessly, because a filename is bytes on a disk rather than text.
- **`ade_core::json`** — a small JSON writer, so the workspace keeps zero dependencies. ADE emits JSON and never parses it, so the whole escaping surface is one function.
- **`Inspection::faults()`** with a typed `Fault` carrying a **stable code** beside its message. Fault computation moved out of the CLI, so the human and JSON outputs cannot disagree about what is wrong with an image, and a future GUI inherits the same list.

- **Fuzz harness (F-001)** — six targets: block parsers, arbitrary-length inputs, the sniffer against mismatched declared sizes, mount-and-traverse, deliberately hostile structures, and truncated/extended images. Deterministic xorshift PRNG so any failure reproduces from its seed; structure-aware mutations (bit flips, field smashes, plausible-but-wrong block numbers) because a parser rejects pure noise at the first field. Hand-rolled rather than `cargo-fuzz`, which needs nightly while CI runs stable — a harness CI cannot run protects nothing against regressions.
- Unbounded *growth* is caught by structural bounds on outputs — a file cannot exceed its volume, a listing cannot exceed the block count — rather than by measuring the heap, since an allocator hook needs the `unsafe` the workspace forbids.
- CI runs the harness on every push. Deep sweeps are `ADE_FUZZ_ITERS=150000 cargo test --release --test fuzz`.
- **IMP-002** logged: OFS data blocks are read without validating `type`, `header_key` or `seq_num`, so garbage headers are silently treated as payload.
- **IMP-003** logged: `walk` and `read_file` are bounded only by their visited sets, with no second line of defence on the AV-001 invariant.

- **OFS data-block validation (IMP-002).** `read_file` checks each block's `type`, `header_key`, `seq_num` and `data_size` against what the table claimed, reporting mismatches through the new `FileContents::faults`. Nothing is refused — the bytes are read regardless (D-012) — but a file that stopped being a file part-way through now says so. Faults are summarised by kind rather than enumerated, coalescing on the discriminant so varied instances of one problem read as one finding.
- `FileContents::is_complete()` now means full-length **and** structurally sound; `is_full_length()` keeps the old meaning.
- `ade extract` reports structural faults on stderr, including when the byte count came out exactly right.
- New `corrupt` fixtures for each fault kind: wrong type, wrong owner, wrong sequence, oversized length, zeroed block.

- **IMP-003 applied** — `walk` returns a `Walk` carrying `hit_limit` and stops at three structural bounds independent of the visited set: entry count, pending directories, and **depth**. Depth was the one that mattered: bounding the count is not enough, because each path is built from its parent's, so a cycle grows the *strings* without bound while the count stays inside its cap.
- Verified by mutation: removing the visited set now yields a clean test failure in one second, naming the seed. The same mutation previously allocated 28.8 GB and the kernel killed the session.

- **`ade check` — the health report (F-010).** Gathers everything knowable about an image's condition in one pass and ranks it by severity: `info` for the cosmetic, `warning` for the odd, `error` for what would lose data. Findings carry stable codes; text and JSON output both available.
- **Bitmap cross-check (AV-003 detection).** `ade-filesystem::bitmap` reads the map — following the rootblock's 25 pointers and the `bm_ext` chain with a visited set, since extension blocks carry no checksum — and the health report compares it against the blocks the directory tree actually reaches. Two directions, two severities: *referenced but marked free* is an error, because the next write destroys live data; *marked used but unreachable* is a warning. Found on a real disk: block 25 of `Rolling Thunder.adf` is a live `T_DATA` block the bitmap says is free.
- **Cross-linked block detection** — a block reachable from two files, which writing either would corrupt.
- **`Volume::file_blocks`** — every block a file occupies, for bitmap cross-checking now and salvage later (F-012).
- **`Volume::geometry`** accessor; `checksum::normal_at` and `checksum::sums_to_zero`.
- **Exit code 5** for `check`: something would lose data. Distinct from 1 because "this disk is odd" and "do not write to this disk" are the two answers a batch run most needs separated.

- **D-010 amended**: the D-002 oracle validates *generated* fixtures, not only real images. ADFlib reads any structurally valid volume regardless of who wrote it, so the loop closes without a corpus — an independent implementation checks the generator as well as the parser, which is precisely the shared-misreading risk the entry was written to worry about. The boundary between the two mechanisms is not *generated versus real*; it is **conformance to the specification versus conformance to reality**.
- **`oracle_fixtures` test, running in CI.** ADFlib and ADE cross-checked on nine generated volumes — all eight dostypes plus a 1.76 MB HD volume, each carrying an accented filename so international hashing is exercised (C-006) — and byte-for-byte on multi-block file contents for both OFS and FFS. CI installs `unadf` and runs it on every push.
- The practical consequence: Phase 2's HD geometry, dostype matrix, LNFS and RDB work is properly verifiable, where it had looked fixture-only. The corpus contains none of those — no HD image, no `RDSK`, no `DOS\4`/`\6`/`\7`, no links in 8865 entries sampled.

- **Phase 2 opened: links and geometry.** Hard links resolve through `real_entry` — bounds-checked (AV-004) and with a visited set, since a looping pointer must terminate the walk not the process. `Volume::resolve` is a no-op on non-links so callers can resolve unconditionally; `read_file` resolves first; `walk` descends a directory link once rather than once per link pointing at it; `ade ls` shows `-> target`, or `BROKEN` with the reason.
- Soft links resolve to an error rather than a guess: they name a *path*, not a block, and AmigaDOS 3.0 removed support.
- **HD (1.76 MB) geometry** verified end to end for both OFS and FFS, with the rootblock computed at 1760 rather than read from the bootblock's misleading 880 (C-007). Extra-cylinder 81–83 geometries too.
- `Entry::next_link`; `FsError::BrokenLink`; `Volume::add_hardlink` in the fixture generator.
- **SPEC §Link block layout**, and the note that `unadf` omits link entries entirely — so link support is validated against the specification alone, with neither an independent implementation nor any corpus material. The one Phase 2 area where both of D-010's mechanisms come up empty.

- **Bitmap rebuild (AV-003, Phase 2).** `Bitmap::rebuild` computes the allocation map a volume should have from the blocks its tree reaches, returning the corrected block contents in memory. **Nothing is written**: D-004 defers write paths to Phase 4, and AV-003 asks for a rebuild to be offered. Correctness is proved by round-trip — build it, read it back, confirm it describes the set it was built from — plus repair of both damage directions and coverage of HD volumes.
- `Bitmap::orphaned` and `Bitmap::referenced_but_free` return the offending **block numbers**, and the health report names them: `Rolling Thunder.adf` now reads "1 blocks are in use by files but marked free (25)". Lists are summarised after six entries, since a report naming 1463 blocks individually is no more useful than one naming none.

- **Hardfiles mount (Phase 2).** `ade info`, `ls`, `extract` and `check` all work on an unpartitioned HDF. A raw volume has no geometry of its own — only the block count matters, since that fixes the rootblock — and ADFlib agrees, reporting an 8 MB hardfile as "Cylinders = 16384, Heads = 1, Sectors = 1". Added to the oracle test, which now cross-checks ten generated volumes.
- **IMP-004** logged: the fixture generator cannot build file extension blocks, so ADE's extension-chain reader is exercised only by real corpus disks — no fixture, and therefore no oracle.

- **IMP-004 applied: the fixture generator builds file extension blocks.** A file's header names 72 data blocks; anything larger chains the rest through extension blocks. ADE has read that chain since Phase 1 — it is how `taterm1` was recovered from a real disk — but nothing could generate one, so the path had no fixture, no test on a fresh clone, and **no oracle**. A 200 KB file now spans six extension blocks and ADFlib extracts it byte-identically to ADE, for OFS and FFS.
- With it, the AV-001 visited set guarding that chain is testable for the first time: `corrupt::extension_chain_loop` and `extension_chain_cycle` build a self-loop and a two-block cycle, and both terminate with a reported cycle. A "next != self" check would catch the first and miss the second.
- The oracle test now covers eleven generated volumes and four content round-trips.

### Changed
- **SPEC §Corpus observations** — new section recording a survey of 4288 TOSEC Amiga ADF images, explicitly labelled measurement rather than specification. Magic distribution, the 300 non-`DOS` images across 144 distinct bootloaders, bootblock-checksum and rootblock validity rates, and the non-canonical size distribution.
- **SPEC §Extended-ADF** — the `UAE-1ADF` layout, derived from eleven corpus images and verified arithmetically (`12 + tracks × 12 + Σ space` equals file size for all eleven). Track type 0 is standard sector data and 1 is raw MFM; `length` is in **bits**, `space` in bytes. Mixed types within one image are the copy-protection signature.
- **C-008** — new constraint: ADF identification is heuristic and must be reported as such. Neither magic, size, bootblock checksum, nor the `DOS` prefix is decisive, and each claim is now backed by a measured figure.
- **SPEC §Geometry** — 80 cylinders is the norm, not the limit; 81/82/83-cylinder images occur and land exactly on `cylinders × 2 × 11 × 512`.
- **D-010** — records that a 4288-image corpus now exists locally outside version control, settling the differential-testing half of the decision in practice; the committed-fixture half stays open.
- **AV-001 widened.** Directory cycles are reachable on structurally valid disks, because AmigaDOS permits hard links to directories. Cycle detection is a correctness requirement for ordinary images, not only a defence against hostile input, and must use a visited-set rather than a depth limit.
- **AV-003 corroborated** by the Linux AFFS documentation, which warns the bitmap-valid flag may be inaccurate after a crash — a routine condition, not only an attack. Noted also that a *set* bitmap bit means *free*, the opposite of the usual convention.
- **F-003** records the sniffing cascade: a plain ADF has no magic number, so content dispatch cannot be a magic lookup.
- Copyright holder in `LICENSE`, `NOTICE`, and workspace `authors` corrected from the bare handle to `Shane Hartley (Darian-Frey)`, so the notice names a legal person. Done before any external contribution, while it is still a one-party change. Recorded under D-011.
- **D-001 → Accepted** (Option A): Rust core exposing a C-ABI bridge, Qt6 GUI over it from Phase 5. The flux/IPF-binding half of the original reversal condition was withdrawn as unfounded.
- **D-002 → Accepted**, scope narrowed to ADFlib alone, decided as a new Option D: reimplement OFS/FFS/RDB in Rust with ADFlib as a **black-box differential-test oracle** — never linked, source never read. Rejects the previously-leaned hybrid, whose safety gap would have made F-001 unclaimable.
- **D-008** — deferral **discharged** and closed out: D-002 inherited no GPL obligation, and the resulting free choice was made the same day (see D-011). The entry stays in the register as the audit trail for the period without a licence.
- ARCHITECTURE, BUILD, SPEC, ROADMAP, FEATURES, ATTACK_VECTORS (AV-005), CLAUDE, and both READMEs updated for the settled stack. BUILD.md now distinguishes build dependencies from test-only ones; SPEC.md records that ADFlib's source is deliberately excluded from its reference list.

### Notes
- The workspace builds, tests (18 passing), lints clean, and documents without warnings. The engine is still a scaffold: no image is parsed yet, and `ade` has no commands.
- Next: the first vertical slice, `ade info <image>` — geometry, dostype, bootblock checksum — chosen over building layers bottom-up so that every seam is exercised before integration rather than after.
- `CLAIMS.md` omitted (non-research); `VOCABULARY.md` deferred (ManifeST contract undefined); `LICENSE` outstanding per D-008. Publication is gated on both `LICENSE` and D-010.

- **RDB multi-partition device support** (Phase 2, F-018 reading half). `ade-filesystem::rdb` parses `RDSK`, the `PART` chain and `FSHD`; `ade-container::Window` presents one partition as a volume. `ade info` reports the drive and its partition table, and `ls`, `extract` and `check` accept `--partition=` by drive name (case-insensitively, per C-006) or index. `Inspection` gains `rdb` and `partitions`; `Health` gains `examined`, naming the volume and partition a report actually covers — a device holds no volume at its own rootblock, so reporting "no volume" and exiting non-zero would have called a sound disk broken.
  - The RDB is **searched for** across the first 16 blocks rather than assumed at block 0, and the `PART` walk carries a visited set, so a cyclic or out-of-range chain is reported as a fault with the partitions found before it kept (AV-004).
  - `Window` re-validates every block number after translating it to the device, so a partition cannot be used to address outside itself — AV-004 holds across the boundary, not only within a volume. `ade-container` knows nothing of RDB; the partition extent is passed in, which keeps D-003 intact.
  - Two units the format makes easy to get wrong have dedicated tests: `SizeBlock` counts **longs** (128 for a 512-byte block), and RDB lists terminate at **-1**, not 0.
  - `ade info` no longer reports a bootblock for a device: block 0 is an `RDSK` structure, and parsing one there produced a confident report about a checksum that was never a checksum.
  - Cross-checked against ADFlib, which reads both partitions of a generated device at the same sector ranges ADE does (`oracle_fixtures.rs::adflib_reads_our_generated_device`).
- `tools/fixtures::device::Device` — builds RDB devices with a partition chain and a minimal `FSHD`/`LSEG` pair. `without_filesystem_driver()` builds the spec-legal shape ADFlib refuses, so that divergence stays visible.
- **SPEC §The oracle is stricter than the format here** — ADFlib will not mount a device without an `LSEG` chain, though FAQ §6.5 says one "isn't needed to reach partitions". Recorded, not resolved (D-012). Also records an ADFlib fill-percentage artefact on multi-block partition bitmaps, so it is not rediscovered as a suspected ADE bug.
- **SPEC §No corpus image carries an RDB** — the `RDSK` signature appears in the first 16 blocks of 0 of 4652 corpus images. The RDB path therefore has no corpus material and rests entirely on the D-002 oracle over generated devices, which is what D-010's amendment exists to permit.
- `ade-endian::i32_at` put to use for `BootPri`, which is signed — routing it through the C-001 seam rather than casting at the call site.

- **Directory cache blocks** (`DOS\4`, `DOS\5`) — Phase 2. `ade-filesystem::dircache` parses the chain hanging off a directory's `extension` field; `Volume::dircache` reads it and `Volume::has_dircache` says whether the volume keeps one. `Rootblock` gains a `dircache` field for the root's chain head.
  - **Fixed a live false positive.** Cache blocks are marked used in the bitmap, and nothing reached them, so the health report counted them as orphaned — 19 blocks on the Workbench 3.1 install disk, 14 on Subwar 2050. All 21 cached disks in the corpus now reconcile exactly, and 20 of them report no findings at all.
  - **The cross-check SPEC asks for.** A dircache duplicates the entry blocks, so `dircache::compare` reports where the two descriptions differ — by name, size, protection, comment, secondary type, or presence — and prefers neither, per SPEC §Directory cache blocks. `ade check` reports the comparison whether or not it finds anything: "compared and matched" is a different fact from "not checked". New finding codes `dircache-disagrees` and `dircache-chain-broken`; `Health` gains `dircache`.
  - Only real directories are searched for a cache. A hard link to a directory has an `extension` field too, and following it would walk whatever happens to be there.
  - Record lengths come off the disk, so both are bounded before use (name ≤ 30, comment ≤ 22) and a record that would run past the block ends the block rather than being invented. The chain carries a visited set (AV-001) and every block number is validated (AV-004). `dircache::parse` is now a fuzz target: 900,000 cases, no failures.
  - The secondary type is **one signed byte** here against the entry block's 32-bit word. `Record::secondary_type_widened` sign-extends, because comparing without it reports every file on the disk as a mismatch.
- `ade-fixtures` builds real dircache blocks for `DOS\4` and `DOS\5`, reading the records back out of the entry blocks that were actually written rather than from the generator's own bookkeeping — a cache assembled from that could agree with the generator while both disagreed with the disk.
- `corrupt::dircache_size`, `dircache_name`, `dircache_drop_last` and `dircache_chain_loop` — a stale cache is the one failure a dircache volume can suffer that no checksum catches, since both blocks still verify. Only the comparison finds it.
- **Oracle: `unadf -c`** lists a directory *from its cache* rather than by walking the hash chains, so it is the only external check that a cache ADE wrote is well-formed. It reads generated `DOS\4` and `DOS\5` volumes identically to their hash-chain listings.
- **SPEC §Confirmed against real disks** — the documented dircache layout verified across 1252 records in 133 blocks over the corpus's 21 cached disks, with zero disagreements. `DOS\4` is now covered by generated fixtures plus the oracle rather than being an open question.

- **SPEC §LNFS field-level pass** — discharges the open question of that name. The long-name entry block, `TYPE_COMMENT` block and root block are now documented at field level with byte offsets. [AOS-LNFS] declares them in C rather than as offset tables, so the offsets are the declaration order laid out; both structures sum to exactly 512 bytes and every field from 0x1F0 onward matches the classic layout, which is what makes the reading checkable rather than asserted.
  - Records the trap the two layouts create together: they share a primary type, a secondary type, a checksum algorithm and their whole tail, so **nothing in the block says which layout it is — only the volume's dostype does**. Read one as the other and the classic name field lands in LNFS's `Spare6` (empty names) while the classic datestamp lands inside `NaC` (name characters parsed as a date). Both blocks checksum correctly either way.
  - **SPEC §The file header is inferred, not documented** — [AOS-LNFS] declares no long-name file header at all. The three file-only fields are placed from the canonical file/directory block shape, which is sound reasoning but not a citation, and is recorded so a future failure is diagnosed rather than rediscovered.
- **SPEC §The oracle cannot check LNFS — it does not implement it.** ADFlib decodes the dostype by bit pattern, so `DOS\6` (`0b110`) and `DOS\7` (`0b111`) are reported as `OFS INTL DIRCACHE` and `FFS INTL DIRCACHE` — the exact trap C-006 and BUG-001 describe. `unadf -c` on a `DOS\7` volume then hunts for cache blocks LNFS never had, fails three checks, prints **an empty listing and exits 0**. Combined with LNFS's absence from the corpus, this leaves it the first structure in ADE with neither corpus material nor an oracle.
- `src/api/tests/dostype_lnfs.rs` — pins the ordering ADFlib got wrong. `Dostype::mode()` matches `6 | 7 => LongNames` *before* testing the dircache bit, so `has_dircache()` is false on LNFS and no cache is looked for. Nothing else can catch a regression here: there is no oracle and no corpus material, and the natural way to write that function is ADFlib's way.
- Corrected the dostype table's INTL column. Bold marks "international while the stored bit is clear", which is `DOS\4`/`DOS\5` only — `DOS\6`/`DOS\7` do carry the bit. The previous bolding implied otherwise and was misleading enough to produce a wrong test assertion before it was caught.
- **D-013** — new decision entry: LNFS is deferred on **verifiability, not effort**. The field-level pass is done and the layout is ready to implement; what is missing is any way to check the result. Identification and hashing stay (correct, corpus-independent, pinned by tests); the block structures are not implemented. One real `DOS\6`/`DOS\7` image, or an LNFS implementation in ADFlib, reverses it.
- `lnfs-unsupported` health finding. A classic read of a long-name block does not fail — it silently yields the wrong name, and still checksums, so nothing downstream notices. `ade check` now says the names are unreliable while block accounting and checksums are not affected. Delivered with D-013, because a silent wrong answer is the one outcome that decision must not produce.

- **SPEC §The wider dostype registry** — survey of Amiga filesystem identifiers beyond the AmigaDOS family, from [AMIGAWIKI], [DISKTYPE], [HYPERION-FS] and [AFFS], cross-checked against the corpus. Two conclusions: **`DOS\0`–`DOS\7` is complete** (no source consulted knows a `DOS\8` or `DOS\9`, so ADE's enumeration needs no ninth case), and the rest of the registry — muFS, PFS/PDS, SFS, AFS, CFS, JXFS, the AmigaOS 4 host-filesystem handlers, Unix and NetBSD types, swap, CD-ROM, `KICK`/`BOOU` — must be identified and declined rather than mounted. Records `SFS\1` as a beta that is format-incompatible with `SFS\2`, and `ID_VP255_DOS_DISK` ("FFS9") as an unresolved lead with no byte value found anywhere.
  - Measured: of 4652 corpus images, 4341 begin `DOS` and **not one** carries any other filesystem identifier. Foreign-dostype handling therefore has no corpus material; it matters chiefly on RDB devices, where `Partition::claims_amigados` is the guard.
  - The muFS open question is narrowed: the identifiers are now pinned, so what remains undecided is scope rather than identification.
- **SPEC §FDI is the licence-free flux format** — FDI (Vincent Joguin, 2000) stores raw low-level track data like IPF, but its specification is public and its tools are open source. C-003 gates IPF behind a licence and forbids ADE from emitting it, so FDI is worth considering as a Phase 4 interchange target alongside SCP (D-007). Not scheduled; recorded so the option is visible when Phase 4 is planned rather than discovered afterwards. Its magic bytes are asserted, not verified.
- **Fixed: a bootblock was reported for containers that have none.** An extended ADF opens with `UAE-1ADF`, so `ade info` was reporting a dostype of `0x5541452d` and "checksum invalid" for a checksum that was never one — the same defect fixed earlier for RDB devices, found by auditing the corpus's 11 extended ADFs during this survey. `Kind::has_bootblock` now decides, and the report says "none — extended ADF has no bootblock at block 0" rather than staying silent. `Unknown` deliberately keeps its bootblock report: 7% of real images have a non-`DOS` bootblock and some still mount (C-008).
- Corpus note: three images (`Shadowlands_Disk2`, `Shadoworlds_Disk2`, `F.1 Manager_Disk2`) carry a bootblock reading `DOS2` in ASCII — dostype byte `0x32`, not a flags value. ADE reports it as `DOS\50 (OFS, INTL, unknown bits 0x30)` with a `dostype-unknown-bits` fault and finds no rootblock, which is the correct outcome: the bits are preserved and reported rather than guessed at.

- **ADZ and HDZ — gzip-wrapped images** (Phase 3, F-003). `ade-container::inflate` implements DEFLATE (RFC 1951) and the gzip wrapper (RFC 1952) from the specifications; the workspace has no dependencies, so there was nothing to reach for. An ADZ now inspects, mounts, lists, extracts and health-checks exactly as the ADF inside it.
  - The container reported is the **inner** one — what the user has is an Amiga floppy, and gzip is how it was stored — with the wrapper reported alongside it rather than hidden: `compressed  gzip, 245130 bytes on disk -> 901120 bytes`. `Inspection` gains `compression`.
  - **The oracle here is stronger than D-002's.** The system `gzip` compresses, ADE decompresses, and the result is either byte-identical or wrong — there is no interpretive gap to adjudicate. A deterministic sample of real corpus images round-trips byte-for-byte, and a damaged stream either errors or reproduces the original exactly, never something in between.
  - **AV-005 is discharged for this path.** The output cap is checked before every write, never after: a 970 KB stream expanding to 1 GB is refused at a peak RSS of 515 MB against the 512 MiB cap, rather than being decompressed and then complained about. Nothing is sized from a declared length — gzip's `ISIZE` is *verified* after the fact, never trusted before it, which is BUG-003's lesson applied where the attacker holds the pen. A back-reference before the start of the output is an error, which is AV-004's equivalent inside the decompressor.
  - `inflate::parse` and `gunzip` are fuzz targets, with a deliberately small cap so a runaway case is caught by an assertion rather than the OOM killer.
  - `examine` unwraps for itself: it reads blocks directly rather than through the inspection, and passing it the still-compressed bytes reported a truncated image on a sound disk.
- **SPEC §ADZ and HDZ (gzip)**, **§Decompression is the AV-005 surface**, **§The oracle for gzip is stronger than the one for ADF** — the header layout, the three rules the inflater is built around, and why gzip's little-endian framing is a deliberate exception to C-001 (which governs *disk* data).
- Two test bugs worth recording, both of which passed on small inputs and failed on real ones: a `gzip` helper that wrote to a child's stdin while nothing drained its stdout **deadlocked** once the compressed output exceeded the pipe buffer, and an "incompressible" test vector built from a weak mixer compressed 22:1 — so the stored-block path it was meant to cover was never exercised. Both now assert the property they depend on.

- **Bootblock banner extraction** (Phase 3, F-011). `Bootblock::text` pulls printable runs from the boot code, filtered so what is reported is prose rather than 68k opcodes — `NqNqNq` is three `NOP`s (0x4E71), and an unfiltered extractor reports mostly padding. `ade info` shows it, `Inspection` gains `boot_text`, and the JSON carries offsets alongside the text.
  - The filters are measured, not guessed: a 10-character floor, rejection of any run that is one unit of ≤ 4 bytes repeated, an 85% "looks like prose" threshold, and dropping `.library`/`.device`/`.resource` names that every bootblock carries. Across the corpus that leaves ~20% of disks with reportable text and **91% of kept runs containing a space** — the measure used to separate prose from code.
  - BCPL-style length prefixes are stripped **exactly**, not heuristically: the leading byte goes only when its value is precisely the length of what follows. `'` is 0x27 = 39, and the message after it in the corpus is 39 characters.
  - What it finds is catalogue material as much as security: `Copylock Amiga (c)1988-91 Rob Northen Computing`, `SKID ROW 1991`, `Cracked by Eagle Soft!`, `Doppleganger's OVERSEER Virus Protector v1.0`.
- **D-014** — new decision entry: bootblock **virus identification is deferred**, and the reason is measured rather than assumed. No checkable signature set is published (the established brainfile CRCs ship as opaque binaries), and matching strain names is **inverted**: all 107 corpus disks that name a virus carry *anti-virus* bootblocks — `CANNOT BE INFECTED BY THE SCA-VIRUS`, `PROTECT AGAINST: BYTEWARRIOR, LAMER Extermin.`, and one virus killer whose menu lists nine strains. Cracking groups installed virus killers routinely, so a name-matcher would flag precisely the disks that were cleaned. ADE reports what the bootblock says and draws no conclusion.
- **AV-002's primary defence recorded as structural.** The vector is *executing* guest boot code; ADE has no interpreter, no emulator and no execution path of any kind. `boot_text.rs` pins this with boot code written to be hostile to a reader — `BRA` to self, `TRAP #0`, all-ones and all-zeros — so the property holds by intent rather than by accident.

- **Format-conversion matrix** (Phase 3, F-016). `ade-core::convert` gives every pair of container formats an explicit answer carrying its own reason — lossless, lossy and what is lost, not implemented and why, or refused and why. `ade formats` prints the matrix; `ade convert <in> <out>` obeys it.
  - **Refused and not-implemented are kept distinct**, because they invite opposite follow-up. IPF output is a licence decision that does not expire (C-003); DMS input is a gap waiting on material (D-009); flux writing waits on Phase 4 (D-005). Reporting them alike would tell someone to wait for something that is never coming.
  - **Lossy conversions are refused outright, not warned about.** Flattening an extended ADF or an SCP capture to sectors discards the copy protection that was the reason to capture it, the loss is not recoverable, and a warning nobody reads is how it happens. No flag enables it.
  - Conversions that run: the decompression direction, whose reader is proven byte-identically against real images — which is exactly what D-004 requires before a write path ships — and copies between sector containers, which differ only by naming convention (SPEC §A raw volume has no geometry).
  - **An existing output is never overwritten.** A conversion that replaces a file is the irreversible damage D-004 is about, and a source image is what someone points this at by accident.
  - The output format is taken from the extension because the file does not exist yet; **inputs are always identified by content**, keeping C-008's habit of trusting evidence over labels.
- **SPEC §Conversion is mostly a question about loss** — why the matrix exists: sector containers are interchangeable byte-for-byte, flux containers are not, and flattening one is a discard that produces a perfectly valid ADF with no record that anything went missing.

- **`FILE_ID.DIZ` surfacing** (Phase 3, F-011). `ade info` reads the disk's own description and prints it; `Inspection` gains `description`, and the JSON carries the text, the stored filename, the block and whether it was truncated.
  - Rare — 0.6% of a 500-disk sample — but disproportionately informative, because it says what the volume name often does not. One corpus disk is labelled `Empty`; its description reads `TEST MATCH CRiCKET SAVE DISK (NEEDED) [2/2]`.
  - Found **case-insensitively**: `file_id.diz`, `FILE_ID.DIZ` and `File_ID.Diz` all occur on real disks, and AmigaDOS filenames are not case sensitive (C-006). The name is reported **as stored**, since what is on the disk is a fact about the disk.
  - Read from the root directory only — the BBS convention puts it there, and searching a whole disk by name is a different feature with a different cost — and capped at 8 KB, because the length comes off the disk (AV-005, BUG-003). The declared size is still reported in full: the cap is on what is read, not on what is claimed.
  - Decoded as Latin-1, so the high-bit box-drawing characters that make up release art survive rather than being mangled as UTF-8. A directory of that name is ignored rather than read as text.

- **Extended-ADF reading** (Phase 4 begins, F-003). `ade-container::extended` parses the `UAE-1ADF` track table; `ade info` reports how many tracks hold ordinary sectors, how many hold raw MFM, and how many hold nothing. `Inspection` gains `tracks`.
  - **`space` is the file allocation; `length` is the meaningful extent.** Measured across all 428 type-0 tracks in the corpus: `length` is 45056 bits in every one — 5632 bytes, one standard DD track — while `space` is 5632, 12650 or 12668 depending on the writer. Reading `space` bytes as sectors would take up to seven kilobytes of padding as data.
  - **A track may hold nothing.** 154 observed type-1 tracks have `space` and `length` both zero: unformatted or never captured, which is a fact about the disk rather than damage to the file.
  - **Damage is a fault, not a failure.** `Demolition.adf` is genuinely 25,732 bytes short, ending inside track 163 of a declared 166; it now yields 163 tracks and a precise report rather than nothing.
  - A wild track count is refused before allocating a table from it (AV-005), and an unknown track type is reported rather than guessed.
- **SPEC §Extended-ADF corrected.** It claimed `12 + tracks × 12 + Σ space` equals the file size "for all eleven" corpus images. It holds for ten — `Demolition.adf` fails it. The arithmetic is the right check, and is what found the truncation, but it is a test a file can fail rather than an invariant. The section also said "a type-0 track reads `space = 5632`", true of only one writer in three.
- **SPEC §The sector tracks really are sectors** — assembling the type-0 tracks of an extended ADF into a plain ADF produces a mountable volume where enough of the disk is ordinary (`Demolition`, `REALM OF THE TROLLS`). This is what confirms the layout rather than merely fitting it: arithmetic can be satisfied by a wrong reading; a legible rootblock at block 880 cannot. It also shows what a type mix means — `Champ, The` is 159 of 160 ordinary tracks, with the one raw track exactly where the rootblock would be.

- **MFM track decoding** (Phase 4, D-005's track model populated). `ade-track` decodes raw tracks into Amiga sectors — sync search, the odd/even split, the sector header, and both checksums. `ade info` reports how much of a raw-track disk is ordinary and how much is protection.
  - **The decode is self-evidencing**, which is a stronger position than anything else in this project. Every sector carries two checksums of its own, so no oracle is needed: **2095 sectors across the corpus's 1235 raw tracks decode with both agreeing**. Confirmed a second way — `Superman - The Man of Steel_Disk2` track 80 decodes as ten sectors that all say track 80, matching their physical position.
  - **The odd/even half order was decided by evidence, not by choosing a source.** Descriptions disagree; both orders were tried against a real track and only one produced matching checksums (odd first). The wrong choice does not fail loudly — it yields plausible bytes and a silently wrong disk.
  - **A track is a bit stream.** Sectors do not begin on byte boundaries: in one `Realm of the Trolls` track every sync sits at bit offset ≡ 7 (mod 8). The first implementation scanned byte-aligned, decoded 8% of the corpus's sectors, and looked like a disappointing disk rather than a broken reader.
  - **A sync mark is not a sector mark.** Three sync words occur throughout the corpus where two is the norm, and miscounting lands in the gap — which decodes to a header claiming format `0xAA` and track 168. More importantly a sync need not have a sector behind it at all: that is how a custom loader finds its own data. Gap decodes to all zeros and **zero satisfies its own checksum**, so a checksum test cannot tell gap from sector; the `0xFF` format byte is the only reliable marker.
  - What this buys, per disk: `Terrorpods` is 95 of 96 raw tracks fully standard — captured raw but not protected. `Wings of Death_DiskB` is 0 of 160, with 6144 sync marks leading nowhere. That difference is now visible rather than inferred.
- **SPEC §MFM** — the sector layout at byte level, the checksum definition, the odd/even formula, and the three traps above, each with the corpus measurement behind it. Closes the "MFM track and sector framing" open question; [RKRM] Appendix C was not needed. **§What this decoder does not check** records the honest limit: clock bits are masked off rather than verified, so MFM encoding violations — a real protection technique — cannot currently be detected.
- Two disks (`Deep Space`, `Terrorpods`) have every raw track claiming to be **track 0**, with checksums fully valid. That is a property of those disks rather than a decoding error, and it is why reconstructing an ADF by physical track position fails on them.

- **Clock-bit verification** (Phase 4). `ade-track::clock_violations` checks the MFM encoding rule itself — a clock bit is set only when the previous and current data bits are both zero — rather than masking clock bits off as the decoder does. `Sector` gains `clock_violations` and `clock_valid()`; `TrackDecode` gains `sync_words` and `clock_violations`.
  - Confirmed exactly on a real sector: **0 of 4095 data clock bits wrong, 0 of 1279 header ones, and 2 wrong in the two sync words**. That last is the point — `0x4489` is deliberately illegal MFM, one violation per sync word, which is precisely what makes it findable where ordinary data cannot produce it.
  - **The clock/data phase is only knowable from a sync word**, since a track's byte boundaries say nothing about where its bit pairs begin. A track with no sync reports `None` rather than guessing a phase and deriving a count from it.
  - Measured: **every one of the corpus's 2095 sound sectors is legally encoded.** There is no illegal MFM inside sectors in this material — these disks protect themselves structurally, with sync marks in the gaps and non-standard layouts, rather than by encoding bytes a drive could not write.
- **A negative result, recorded rather than shipped.** Subtracting the sync-word count from a track's total violations looked like an illegal-MFM protection indicator. It was implemented, measured, and **abandoned**: a sync word does not contribute exactly one violation, because the transitions into and out of a sync region contribute their own — a known-good Terrorpods track has 22 sync words and 27 violations. Counting the baseline two different ways produced two contradictory pictures of which disks were protected, the first making the *most* heavily protected ones look cleanest. ADE reports the raw counts, which are facts, and derives no score from their difference. SPEC §A violation count is not a protection score records why, so it is not reinvented.

- **Raw-track + filesystem dual view** (Phase 4, F-007). `ade-core::assemble` reconstructs a plain image from whatever a raw-track container yields — ordinary tracks as they are, raw tracks MFM-decoded — so an extended ADF is reported *both* as a track table, which is what it is, and as a volume, which is what most of it holds.
  - **Six of the corpus's eleven extended ADFs now mount**, and their content was previously unreachable by any part of ADE: `Demolition` gives 29 files and 560 KB, `REALM OF THE TROLLS` 8 files and 372 KB, `BDC A` and two disks whose volume is named `protec`. `ls`, `extract` and `check` all read through the reconstruction.
  - **Sectors are placed by physical position**, not by the track number they claim. `Deep Space` and `Terrorpods` label every raw track as track 0, so trusting that field would pile a whole disk onto track 0 — which is also why those two assemble to nothing usable despite decoding over a thousand sectors each.
  - **It is a reconstruction and says so, everywhere it is shown.** Undecodable sectors read as zeros, so a listing can silently omit half a disk. `ade info` reports `880 of 1760 sectors (50% of a disk)` before the volume, and `ade check` adds a `volume-reconstructed` finding — because "880 orphaned blocks" means something quite different on a disk half of which was never recovered, and the existing message ("lost space, or deleted files") would have been wrong in both halves.
  - A container with nothing readable reports no volume rather than an empty one: an image of pure protection has no filesystem view to offer, and inventing one is worse than saying so.
  - `examine` inspects the **original** bytes and reads blocks from the reconstruction. Inspecting the assembled bytes reported a protected disk's container as a plain ADF.

- **MFM encoding and extended-ADF writing** (Phase 4). `ade-track::encode_sector`/`encode_track` are the inverse of the decoder, and `ade-container::extended::write` emits the container. `ade convert --raw in.adf out.adf` writes a sector image as raw MFM tracks.
  - **Verified by round-trip, which is what D-004's ordering buys.** The read path was proven first — 2095 corpus sectors decoding with both of their own checksums agreeing — so the decoder is a trustworthy judge of the encoder. A whole disk encoded track by track, written, read back, decoded and reassembled comes out **byte-identical** and mounts under its own name: 1760 of 1760 sectors, 160 of 160 tracks standard, 0 stray syncs.
  - **Clock bits are computed, not left clear.** This is the part a test helper can skip and a real encoder cannot: a clock bit depends on the data bit before it, so the body is written as one continuous stream and the clock pass runs over the whole of it. The sync words are excluded deliberately — their illegality is what makes them findable.
  - A sector is emitted at the documented **1088 bytes**: four of lead-in, four of sync, 1080 of body. An earlier version put the lead-in in the gap and emitted 1084, which read back correctly but did not match SPEC.
  - `--raw` is a flag rather than an output extension, because an extended ADF is also called `.adf`. The format has no distinct extension and inventing one would be presumptuous.
  - The conversion matrix records sector image → raw MFM as **lossless**, which it provably is. The reverse stays lossy: flattening an extended ADF discards raw tracks that *could* hold protection, and the matrix is conservative about that even when they happen not to.
- An independent confirmation of the earlier negative result: this encoder produces a perfectly-formed track with **22 sync words and 28 clock violations**, matching the 22-and-27 measured on a real Terrorpods track. Sync *boundaries* contribute violations of their own, which is exactly why "violations minus sync words" is not a protection score (SPEC §A violation count is not a protection score).

- **Consolidation and diffing** (Phase 4, F-008 and F-009). `ade-core::consolidate` merges several dumps of one disk sector by sector and reports where they disagree; `ade-core::diff` locates the differences between two. `ade consolidate a.adf b.adf ...` and `ade diff a.adf b.adf` expose both. Consolidation is **report-only by default** — writing a merged image needs `--output=`, and never overwrites an existing file.
  - **A correction: this was previously recorded as blocked on material, and that was wrong.** The corpus holds **46 titles whose dumps genuinely differ**, several with six versions. Six dumps of Workbench v1.0 give 1400 sectors agreed, 348 resolved by plurality and 12 tied.
  - **It reports agreement, not correctness.** F-008's wording — "merge N reads of the same disk into a best-estimate image" — assumes the reads came from one physical disk, so a disagreement means a read failed. The available material is not that: these are independent dumps of possibly different copies, and several are TOSEC-tagged `[m files moved]` or `[m startup-sequence]`, i.e. deliberate edits. One corpus pair differs in exactly one sector — block 880, the rootblock, by 17 bytes, which is a volume datestamp. Neither dump is wrong. So the tool names the disputed tracks and how the votes fell, and declines to pronounce a winner correct; the CLI says so in as many words.
  - **Two dumps cannot vote.** With two sources every disagreement is a tie by definition, and the report states that rather than presenting arithmetic as judgement.
  - Merging is **per sector**, reporting **per track**. Differences are often confined to one sector, so merging whole tracks on a plurality would discard good sectors along with the disputed one; F-008 asks for a per-track report and that is what is given.

- **Corpus-scale batch operations** (Phase 5, F-014). `ade batch <dir|image>...` verifies a whole corpus in one pass and reports a histogram — containers, findings, how many mounted, how many are sound, bytes recovered — in text or JSON. Records stream as JSON Lines followed by a summary object; progress goes to **stderr** so stdout stays clean when piped.
  - **The full 4652-image corpus runs in 5.5 seconds at 9 MB peak RSS.** One image is read, examined and dropped, so memory does not scale with the corpus. 3601 mount (77%), 2847 are sound (61%), none is unreadable, and 2.2 GB of file content is recovered. This is the capability every corpus measurement in SPEC was taken by hand-rolling a script for.
  - **Nothing aborts a run.** An unreadable image becomes a record rather than an error: a pass over four thousand disks that stops at the first bad one has reported on one disk. Results are in sorted path order, so two runs are comparable and a failure is reproducible.
- **Fixed: `bitmap-flag-clear` was reported twice.** It was raised both as an `Inspection` fault and again by the health report's bitmap cross-check, so `ade check` listed the same warning twice in slightly different words. **Found by the batch histogram** — the code appeared on exactly twice as many images as carried it, which is the sort of pattern only a corpus-scale view makes visible.
- **Fixed, in the batch report itself: findings are counted once per image, not once per occurrence.** A damaged disk can raise `data-block-structure` dozens of times; summing those made **186 affected images read as 1050**. Caught by cross-checking two suspiciously equal totals in the feature's own first run over the corpus.

- **SCP is no longer blocked on material** (Phase 4, D-007) — a reversal of an earlier judgement, recorded here because the judgement was wrong rather than merely outdated. The Greaseweazle host tools (`gw`) convert a plain sector image into real SCP, so every one of the 4652 corpus ADFs is potential material; and because `gw` is an independent implementation, it is an **oracle** in exactly the sense D-002 and D-010 mean. Verified: five varied disks round-trip ADF → SCP → ADF **byte-identically**, HFE does too, and ADE's sniffer already identifies a generated SCP as `SCP flux`.
  - **Generation is not deterministic.** Converting one ADF twice yields two different SCP files — flux timings carry jitter, which is the point of the format. An SCP fixture therefore cannot be committed and compared byte for byte; it must be generated at test time, with the **round trip** as the invariant. That suits D-010, which commits no binaries anyway.
  - **`gw` does not understand extended ADF**, and fails silently. Given a 2,004,560-byte `UAE-1ADF` container it read the first 901,120 bytes of the *file* as sectors — header included — and reported "Found 1760 sectors of 1760 (100%)". The round trip is self-consistent and the input reading is nonsense. It is an oracle for plain sector images only; pointed at a raw-track container it agrees with itself about the wrong data.
  - C-003 gains independent corroboration: `gw` writes SCP and HFE but refuses IPF as an output format.
  - Greaseweazle is **not on PyPI** — `pip install greaseweazle` fails. It installs from the project's own releases or git.
- **SPEC: removed a duplicate empty `## Flux formats` heading** left by the edit that inserted §MFM.

- **Auto-identification against TOSEC** (Phase 5, F-013). `ade-catalogue` parses Logiqx XML datfiles and indexes them by CRC32; `ade identify --datfiles=DIR <image>...` names images by content, and `ade batch --datfiles=DIR` catalogues a whole corpus in one pass.
  - **4586 of 4652 corpus images identified (98%)** from 88,921 entries across 98 Amiga datfiles. What it recovers is what a renamed file has lost: `1000cc Turbo.adf` becomes `1000cc Turbo (1990)(Energize)[cr CSL][t +3 Supplex]`, and `Karate Master.adf` becomes `Karate Master (1994)(Maddison, Rob - F1 Licenceware)(LW)[h Nemesis][AMOS]`.
  - **CRC32 is a content hash, not an identity.** Measured before designing around it: **71 collisions among 88,833 entries**, and size does not separate them — the colliding pairs share a length. None involves an `.adf`, and no corpus image lands on one, so the risk is theoretical today rather than absent. `identify` therefore returns **every** match and reports when there is more than one, rather than choosing.
  - A scanner rather than an XML parser, since ADE has no dependencies and the shape is narrow. Attributes are read **by name**, so attribute order cannot break it, and the five XML entities are resolved — only `&amp;` occurs, 8772 times.
  - Cost over the corpus: 13 seconds and 76 MB, against 5.5 seconds and 9 MB without. The dataset load is **0.17s** of that; the remainder is CRC32 over 4.2 GB of image data, which is inherent.
- **CRC32 moved from `ade-container::inflate` to `ade-block::checksum`**, with a re-export left where gzip callers expect it. Two unrelated parts of ADE need the same algorithm — gzip verifies a decompressed image with it, TOSEC identifies one — and implementing a checksum twice is how two copies of it silently diverge. `ade-block` is the lowest layer both can reach.
- **Layering policy amended** so `ade-catalogue` may depend on `ade-block`. A deliberate edit to `tools/check-layering.py`, which is what that file exists for: the point of the policy is to make a cross-layer edge visible in review rather than impossible.
- `.gitignore`: `/datfiles/` — freely redistributable metadata rather than disk content, but 31 MB of someone else's dataset does not belong in this repository any more than the images do. The parser is what ADE owns.

- **C-ABI bridge** (Phase 5, D-001). `bridge/` exposes ADE's core over a C ABI — the seam the Qt6 GUI will link against, and the **only place in ADE that writes `unsafe`**. Opaque handles, explicit free functions, and flat error codes rather than a Rust `Result`.
  - **The `unsafe` exemption is scoped, not granted.** The workspace *forbids* `unsafe_code`, and `forbid` cannot be lifted by an inner `allow` — that is the point of it. So the bridge crate opts out of the workspace lint set entirely and restates every other lint verbatim, which keeps the exemption visible in one `Cargo.toml` rather than weakening the policy for every crate.
  - **No panic crosses the boundary.** Unwinding into C is undefined behaviour, so every entry point is wrapped in `catch_unwind` and returns a null or a code. The workspace already denies panicking constructs; this is belt to that's braces, because "should not panic" and "cannot unwind into C" are different claims.
  - **Names are bytes, not C strings.** Amiga filenames are Latin-1 and routinely hold bytes above 0x7F — `äpfel` is in the corpus. Handing those out as `char*` would either lie about the encoding or mangle the name, so anything that came off a disk is an explicit pointer-and-length `AdeBytes` and the caller decides how to decode it. Only ADE's own diagnostics, ASCII by construction, are `char*`.
  - **Null is tolerated at every entry point**, including the free functions, because a C caller that has just had an error will pass one.
  - `bridge/include/ade.h` is **hand-written**. ADE has no dependencies, and a header is the contract with every future caller: worth reading and reviewing, and small enough that generating it would buy nothing.
  - Verified three ways: 8 Rust tests; a real C program compiled with `-Wall -Wextra -Werror` against the header, which is the **only** thing that can catch the header disagreeing with the library; and that program under AddressSanitizer, UBSan and LeakSanitizer — clean, no leaks.
  - CI runs the C check on every push. It generates its own image with the new `mkfixture` tool, since D-010 commits no binaries and there is therefore no `.adf` in the repository for it to use.
- `tools/fixtures --bin mkfixture` — writes a standard test image to a path, so things that are not Rust can get a real image to work on.
- `tools/check-layering.py`: `ade-bridge` may depend on `ade-core` and nothing else, the same rule as the CLI — no engine logic can leak into a binding (F-002).

- **Qt6 GUI** (Phase 5, F-004, D-001). `gui/` is the front end ADF Opus never got: a directory tree with name, size, modified date and protection flags, hex and text views beside it, drag an image in to open it, drag a file out to extract it, and search by name across every image that is open. CMake builds it against the C ABI; `cargo` is invoked for the bridge from CMake, so there is one command to build the application.
  - **Nothing in the GUI knows anything about Amiga filesystems.** Every fact on screen arrived through the C ABI. That is the point of the split (F-002): the window cannot drift from the CLI, because there is one implementation underneath both.
  - **Search made the bridge grow, not the GUI.** Searching means walking a disk, and safe traversal is cycle detection (AV-001) plus a depth bound (IMP-003) — engine logic. So `ade_walk_open` was added to the ABI, returning every entry with its full path, and `ade.h` documents it as existing precisely so no front end writes its own traversal. A GUI that reimplemented the walk would hang the window on a crafted image while the CLI shrugged it off.
  - **Several images stay open at once.** Each is a root in the tree; opening a second no longer displaces the first, which is what makes a cross-image search mean anything. Measured on 400 real corpus images: 580 ms to open all of them, 79 ms to search all of them (7908 matches), 400 MB resident — an image is held in memory while it is open, so this scales with images open, not with corpus size.
  - **Directories are read when opened, not walked up front.** Most images are glanced at, and walking a whole disk to show a root listing is work nobody asked for. Search is the deliberate exception, and it says how long it took.
  - **A drag writes the file at the moment the drag starts.** Handing bytes to a file manager means offering `text/uri-list`, which means a real file must exist; extracting every selection in advance would read files nobody drags anywhere. A directory produces no URL at all, because a zero-byte file named after a drawer is worse than a refusal.
  - **The window raises no dialogs.** It emits `errorOccurred`; `main.cpp` decides errors are dialogs. The first version called `QMessageBox::warning` directly and hung the test suite — a modal blocks until someone clicks it, so every failure path was untestable. The fix was a design change rather than a test workaround, and it leaves the error UI to whatever links the window.
  - **14 headless tests** under `QT_QPA_PLATFORM=offscreen`, needing no X server, and compiled `-Wall -Wextra` clean. A GUI is usually excused from testing on the grounds that you have to look at it, which is true of how it *feels* and false of what it *shows*.
  - **Looking anyway caught four defects the tests could not have**, each found by rendering the window offscreen against real corpus disks and reading the result. The Modified column truncated to `1990-09-20 17:...`, hiding the only part of a timestamp nobody can infer. An image row wrote its container into *Modified* and its volume name into *Protection* because the columns were free, so a disk appeared to have been last modified in "ADF (DD, 80 cylinders)" — image rows now span, and say what an image actually has. `sortItems` sorts every level of a tree, so the images themselves came out alphabetically rather than in the order they were opened. And a row stayed highlighted in the tree while the views showed a search result from a different disk, with the byte count the only clue that the two were unrelated — the two trees now hand the selection between them.
  - The test image comes from `mkfixture`, built by CMake before the tests run, since D-010 commits no binaries.
- **IMP-005** — new improvement entry: an open image is held whole in memory, so the GUI's resident size scales with images open (400 MB for 400 floppies). Suggested, not applied: the ceiling is total bytes rather than image count, and a 500 MB hardfile reaches it alone, but every fix trades against ADZ/HDZ behaving identically to a plain container.

- **SCP flux reading** (Phase 4, F-003, F-007, D-007). `ade-flux` was a seven-line stub; it now parses the SuperCard Pro container and turns flux intervals into an MFM bit stream, which `ade-track` already knew how to find sectors in. A capture opens, mounts, lists, checks and extracts like any other image — `ade info` on a 30 MB file takes 0.4 seconds.
  - **Two byte orders in one format.** The header, track table and revolution entries are little-endian; the flux values are big-endian. `009e` is **158** read one way and **40448** read the other, and only 158 ticks × 25 ns is an interval a drive produces — the wrong choice does not fail, it silently finds no sectors anywhere. So `ade-endian` gained little-endian readers rather than letting one call site write the exception inline, and `clippy.toml` gained the `from_le_bytes` entries it had never needed: **C-001's tripwire had a hole for exactly as long as nothing ADE read was little-endian.**
  - **The bit-cell width is not in the file.** Recovering bits means deciding how many cells each interval spans, and motor speed drifts a percent or two within one revolution — enough for a fixed divisor to accumulate drift until an interval lands between two and three cells, where one rounding error costs every sector after it. So the cell width is tracked by a slow phase-locked loop.
  - **Two ways that loop can lie, both found by tests rather than by reasoning.** A correction of one sixteenth of one tick is **zero** in integer arithmetic, so on a drive 2% slow the loop never moved — while reporting *perfect* lock, because the drift it measures stayed at zero. And flux at a data rate nothing like MFM rejects every interval, so the estimate is never corrected, never drifts, and again reads as a perfect lock. A loop that never ran is not a loop that succeeded. The estimate is now carried at 64× so sub-tick corrections accumulate, and "locked" means small drift **and** under 5% of intervals rejected.
  - **Every stored revolution is merged, not chosen between.** An SCP normally holds two or more revolutions per track, and they are not duplicates: a marginal region reads differently each time, which is *why* the format stores several. Each is decoded and any sound sector still missing is taken. That is F-008's merge inside one file, and the concrete reason reading flux beats reading a sector image of the same disk — the sector image already threw away the second opinion.
  - **The disk-type byte cannot be used for detection.** The specification assigns 0x04 to Commodore Amiga; Greaseweazle writes 0x80, "other", for a disk it has just encoded as AmigaDOS MFM. A reader dispatching on it would refuse the standard tool's own output. Reported, never acted on — the same lesson C-008 taught about the `DOS` prefix.
  - **A capture now says how it was captured**, separately from what it holds: revolutions, resolution, RPM, index alignment, and whether the timings were **normalised** — the one line a preservationist should read twice, since a normalised capture has already had the jitter that carries weak bits averaged out of it.
  - Verified against `gw` as an independent implementation (D-002's oracle rule, applied to a second format): a generated fixture and three corpus disks round-trip **byte-identically** through ADF → SCP → ADF, and 20 corpus disks produce identical listings, every one recovering **1760 of 1760 sectors** with a single out-of-range interval per track — the partial cell after the index pulse. 22 new tests in `ade-flux`, 4 in `ade-core`, one of which needs neither `gw` nor a corpus: `ade-track` can *encode* a track, so the bits can be turned into the flux a drive would have seen and read back.
  - **What none of this establishes is anything flux exists for.** `gw` encodes ordinary AmigaDOS disks, so these captures hold no weak bits, no long tracks and no deliberate illegality. "ADE reads a clean capture correctly" is necessary and nowhere near sufficient; only real protected media closes that gap, and that needs the hardware F-006 waits on.
  - **SCP → ADF conversion stays refused**, unchanged: F-016 refuses lossy conversions outright, and flattening flux to sectors is the definition of one. Browsing the capture directly is the answer, and now it works.
  - **BUG-008** — new: `ade formats | head` panics on a closed pipe. IMP-001 fixed exactly this for `info` and `ls` in August; `formats` was written afterwards and never routed through the `emit` helper that exists for it.

### Fixed
- **BUG-008 (low)** — `ade formats | head` panicked with `failed printing to stdout: Broken pipe`. Checking the other arms found the same thing in five more: `--help`, `--version`, `convert`, `diff` and `consolidate` — **every command written after IMP-001 fixed this for `info` and `ls`, and none written before it.**
  The defect is not that one command used `println!`. It is that the rule lived only in a doc comment — one which already claimed "every line of output goes through here" while six commands did not — so each new command had to rediscover it. Three things changed accordingly: the direct writes are gone; `emit_lines` exists for the common case of a block of output, so the pattern to copy is one call rather than a loop somebody might forget to write; and `cli/tests/pipes.rs` runs commands into a reader that stops, asserting none exits 101.
  **The test was checked against the bug, not just against the fix.** Restoring `println!` in `formats` makes it fail with `` `ade formats` panicked when its output was not read ``. A regression test that has never seen the regression is a guess.
  **A consequence worth knowing:** `println!` flushes on every newline and a locked writer flushed once does not, so `--help` never panicked in practice even before the fix — 1.5 KB fits the 64 KB pipe buffer and the writer never learns the reader has gone. `formats` panicked because it met the closed pipe on line two. That makes the integration test a net rather than a proof, which is why the deterministic check on `emit_lines` lives in `main.rs`'s own tests, against a writer that fails on demand.
  Output verified **byte-identical** before and after for all five reporting commands.
- **BUG-007 (medium)** — `--format=json` was accepted and silently ignored by `diff`, `consolidate`, `identify` and `formats`. Fixed by emitting rather than by rejecting: all four honour it now, `identify` as JSON Lines like `batch`.
  The shapes were the part worth thinking about, since F-015 makes them a commitment the moment they ship. **The conversion matrix is keyed on codes, not prose** — `Kind` gained `code()` (`adf`, `extended-adf`, `scp`), because `Display` yields `ADF (DD, 80 cylinders)`, a sentence carrying a geometry that varies between images of one kind; matching on that is parsing prose, so the display strings sit alongside as `from_label`/`to_label`. **A conversion separates `kind` from `reason`**, because F-016's distinction between *refused* (a decision that does not expire) and *not implemented* (a gap with a cause) invites opposite follow-up and a caller should not have to read English to tell them apart. **`consolidate` reports `can_vote`**, false with two dumps, because every disagreement between two ties by definition and a caller ranking by `unresolved_sectors` would otherwise call every two-dump run the most broken thing it had. **`diff` lists which sectors moved**, not merely how many. **`identify` returns every match with `ambiguous`**, since CRC32 is a content hash and 71 collisions were measured within the dataset.
  **One inconsistency found and documented rather than changed:** `diff`'s sector numbers are absolute while `consolidate`'s are within their track — sector 2 of track 1 is absolute sector 13. Both are right where they sit; it is now said in the contract instead of waiting to be discovered by comparing two outputs of one disk.
  **`--output`'s confirmation moved to stderr under JSON only**, because a line of prose in the middle of a JSON document means it is not one. The first attempt moved it for both formats and an existing test caught it: fixing the JSON surface is no reason to move a line a text-mode script may already be reading.
  Verified: 400 corpus images through `identify --format=json` gave 400 valid JSON Lines, zero malformed, zero non-ASCII; 50 documents from `diff` and `consolidate` over corpus pairs, zero malformed; and the text output of all four is byte-identical to before. 12 new tests, the CLI half checking the flag *changes what comes out* — a test asserting only "exit code 0" would have passed throughout the bug's life.

- **The JSON surface is versioned and the version is enforced (F-015 met, D-015).** F-015 had promised since August that "field names and fault codes are stable", with nothing behind the promise — and a rename is the one breakage that does not fail loudly, because a consumer reading a key that has vanished sees a missing *value*, not an error, and carries on with a wrong answer.
  - **Every document carries `schema` as its first field**, including each line of a JSON Lines stream. Versioning only the summary of such a stream fails in exactly the case the stream exists for: a consumer reading record by record, or resuming an interrupted run, has no summary to consult. Twelve bytes a line.
  - **Added at one point, not by each builder.** Being a document is a property of reaching stdout, not of a value: `Inspection::to_json` is a whole document under `ade info` and a nested field under `ade check`, and a version stamped inside it would appear twice in the second case on an object that is not a document. `Value::versioned()` is called by the CLI's single JSON emission path — the same answer BUG-007 and BUG-008 both pointed at, since each was one omission repeated across commands added later.
  - **Major means renamed, removed, retyped, or redefined under an unchanged name** — that last being the dangerous one. **Minor means added.** The surface starts at **1.0**.
  - **The inventory is what makes it real.** `src/api/tests/schema.rs` lists every field path ADE can emit, per document; any change fails it, and the fix is to edit the inventory *and* move the constant in one commit where a reviewer sees both. Same shape as `tools/check-layering.py` and `clippy.toml`: not "this cannot change" but "this cannot change quietly". A version nobody bumps is worse than no version, because it asserts a stability that is not being maintained.
  - **Writing the inventory found two defects rather than paperwork.** An empty array shows none of its element fields, so a clean fixture would have inventoried `findings` as a leaf and quietly stopped covering `findings[].code` — every document now has an input that produces its optional parts, including a damaged image and a partitioned device. And **`batch`'s summary keyed its findings on fault codes**, so the document's shape changed with the data: a healthy corpus and a broken one emitted different fields, which no inventory can pin.

### Changed
- **`ade batch --format=json`: the summary's `findings` is now an array of `{code, images}`** rather than an object keyed on fault codes, matching `containers` alongside it. A breaking change to that one field, made deliberately **before** the schema was declared 1.0 rather than needing a major version afterwards. Dynamic keys are now excluded from the surface by policy: a document whose fields depend on the data cannot be inventoried, and could not be held to D-015.

- **RDB partitions in the GUI** (Phase 5, F-018). A hard disk opens as its partitions, each with its files beneath it, and search covers every one. Reading has worked since 2026-08-24; what was missing was any way to see it short of `--partition=` on a command line.
  - **Partitions are a level of the tree, not a menu.** A device holds no volume of its own, so the window shows the partitions it does have. A picker would have made a disk look like one volume with a switch beside it — which is the partition-blind assumption, and the one to avoid.
  - **The ABI grew a selector rather than a second family of calls.** `ade_dir_open`, `ade_walk_open` and `ade_file_read` each take a partition index or `ADE_WHOLE_IMAGE`. A device is not a special case of an image; it is what an image is when it has an RDB. Existing callers changed rather than new functions appearing, which the header being four days old made cheap and a year from now would not have.
  - **A partition is not an offset.** It carries its own block size and reserved-block count, and the rootblock is computed from both (C-007) — so `ade_partitions_open` reports the computed `root_block` and the reading calls take an index. A front end adding `first_block` to an assumed layout would miss the rootblock of any partition reserving other than two blocks, and the header now says so.
  - **Whether a partition mounts is reported separately from whether it is bootable.** They are different questions and the first is the useful one: a partition can be flagged bootable and hold nothing, or hold a good volume and not be bootable, or be `PFS\0` — a real partition ADE cannot read, where an empty listing would read as an empty disk.
  - **Two more defects from looking at the window.** A device's row reported `no rootblock at block 4096`, the volume-absent reason, which on a sound hard disk reads as damage; it now says how many partitions there are and how many mount. And the search result column now names the partition, not just the image — the fixture deliberately puts a `readme` in both partitions, since one name in two volumes of one disk is precisely what a partition-blind reader gets wrong.
  - 5 new ABI tests, 3 new GUI tests, and the C smoke test now runs against a hard disk as well as a floppy — in CI too, since nothing else exercises the partition calls from C.

### Fixed
- **The GUI's test fixtures went stale whenever the generator changed.** They were declared to CMake as build *outputs*, so an existing file was considered up to date however old it was: a test asserting on what `mkfixture` had newly been taught to write failed against the image written before it, and the failure looks like a bug in the window rather than in the build. They are regenerated on every build now, like the bridge above them — cargo is incremental and knows whether anything changed; CMake, given only an image path, does not.
- **The C smoke test skipped hard disks entirely.** It bailed as soon as an image reported no volume of its own, which is the normal state of every device, so the partition calls would have had no C-side coverage at all. The volume check now comes after the partition table.

- **IMP-006 applied — the C ABI no longer rebuilds the image on every call.** `AdeImage` holds the mounted `Image` instead of the raw bytes, and the health count is computed once at open. The cost being removed was never the copy: `Image::from_bytes` reassembles the container, so every directory expansion re-decoded 160 tracks of an SCP or re-inflated an ADZ, and `ade_image_finding_count` ran a full health check — bitmap cross-check and all — each time a GUI drew a badge.
  With two 30 MB flux captures open: expanding 84 drawers **8681 ms → 63 ms**, selecting 84 rows **11023 ms → 1115 ms**, searching **839 ms → 1 ms**, dragging out 12 files **1276 ms → 0 ms**.
  **It cut memory rather than trading for it**, which is the opposite of what caching usually costs: four captures held **153.6 MB → 36.8 MB** resident, below their on-disk size, because what is kept now is the assembled 880 KB volume rather than the flux it came from. IMP-005's figures improve for every container that is not already a plain ADF.
  **The mounted image had to become optional**, and the first version got it wrong: it returned null for a container ADE cannot mount, which would have made the GUI refuse to describe exactly the disks a person is puzzled by — a quarter of real images hold no AmigaDOS volume, and the container and the reason are the whole point of opening one. Two tests pin it: an unmountable file still opens and reads back null rather than crashing, and the cached finding count is checked against `examine`'s own answer rather than against itself, since a cached number's failure mode is becoming a *different* number.
- **Phase 1's deliverable list corrected.** Three boxes were still unticked — mounting OFS and FFS, the health report, and validation against three fixtures — all of which had been done for days, one of them duplicating a ticked line two rows above it. The phase's status still read "first vertical slice landed", while the paragraph below it said acceptance was met. The 2026-08-28 audit checked FEATURES statuses and the per-phase scope lines and did not look at the checkboxes; this is the same class of staleness one layer down.

- **SHA-1 ([RFC 3174]) in `ade-catalogue`, and a correction it produced.** F-013's remaining datasets turned out to be a dead end (D-016), so the work went to the dataset already in hand: every one of the 88,921 TOSEC entries carries MD5 and SHA-1 as well as CRC32, and ADE indexed only the CRC32.
  - **The claim that motivated it was wrong, and the measurement is the deliverable.** ADE had recorded since 2026-08-27 that the dataset held "71 CRC32 collisions", and `identify` returned every match and declined to choose. Checking it: **77 groups share a CRC32 and a size, and every member of every group carries the same SHA-1 *and* the same MD5.** They are duplicate content under different names — the same CD audio track as track 6 and track 10, the same ISO in two sets — and there are **zero** collisions. Not one group involves an `.adf`. The claim appeared in nine places across the registers and the source; all are corrected.
  - **So the useful thing is not resolving ambiguity but naming it.** `identify_detailed` classifies several matches as `duplicated` (one file, several names, every one correct), `collision` (different content claiming one CRC32 — the disk in hand is none of them), or `unverified` (the dataset offers no SHA-1 to tell). Reporting duplicates as "ambiguous" said ADE could not tell which disk it held, which was never true.
  - **SHA-1 runs only when more than one candidate survives**, which across 4,652 images is never: identification still costs 8 s and 72 MB over the corpus, unchanged. Hashing every image twice to serve a case that does not occur would have taxed every disk to help none.
  - Written from the RFC rather than pulled in, and checked three ways: the RFC's own vectors, the empty input, every length from 0 to 200 against `sha1sum` — covering both padding cases, including the one needing a second block — and an 880 KB disk-sized input. C-001's tripwire fired while it was being written and caught a real slip: the first draft assembled the message schedule by hand with shifts, a big-endian read the lint cannot see. It reads through `ade_endian::u32_at` now, and `ade-endian` gained `put_u64`.
  - **JSON gains a `match` field**, and the schema moves **1.0 → 1.1** — the first exercise of D-015's policy, and it worked as intended: the inventory test failed, the fix was to edit the inventory and the version together in one commit. `ambiguous` keeps its old meaning ("more than one entry") rather than being redefined, which would have been a major change.

- **Bulk convert (F-014's last clause).** `ade batch --convert=<code> --output=<dir>` converts a whole corpus in the same pass as the health check, from the bytes already read — converting separately would read all 4.2 GB a second time to produce a report ADE has just produced. **400 real images to extended ADF in 1.36 s at 9.7 MB peak**, memory flat as ever, and 30 spot-checked outputs list identically to their sources.

Each outcome is reported per image with its reason and counted in the summary, because "412 refused" without a reason sends a person back to run the command again per image.

- **Identification on open (F-013's last clause).** `ade info`, `ade check` and the GUI name a disk as it opens, from the bytes already read, rather than only when `ade identify` is invoked.
  - **Configured rather than automatic, and the measurement decided it.** Loading 88,921 entries takes **140 ms**; `ade info` itself takes under ten. Identifying unconditionally would make the fastest command in the tool fourteen times slower for everyone, so a dataset is looked for in `--datfiles=`, then `$ADE_DATFILES`, then `$XDG_DATA_HOME/ade/datfiles` — and when none is configured, nothing loads and nothing costs anything. A path that does not exist is treated as no dataset rather than as an error: an unset-up machine should run ADE, not refuse to.
  - **The GUI is where the clause pays.** The dataset loads once for the session and every image opened afterwards arrives already named — cost paid at startup, spent on every disk. Scripted corpus use should still use `batch --datfiles=`, which loads once instead of once per image: a second against thirteen minutes over 4,652 images.
  - **The ABI identifies at open because it cannot identify later.** `ade_image_open` takes a catalogue (which may be null), and the name is decided while the bytes are in hand — the handle keeps a mounted image rather than the file (IMP-006), so it has nothing to hash afterwards. That is the clause's own wording turning out to be the only implementation available.
  - **`mkfixture --datfile` writes a dataset matching the image it generates**, with **its own CRC32 implementation**. The layering check refused the obvious shortcut of borrowing `ade-block`'s, and it was right to: D-010 keeps the fixture generator dependent on nothing so a misreading in a layer crate cannot cancel out against it, and that applies to the checksum a datfile is matched on as much as to the disk. If the two implementations ever disagree the identification test fails, which is exactly the signal the independence exists to give.
  - Schema **1.3 → 1.4**: the inspection document gains `identified`. 483 tests, 19 of them in the GUI.

- **D-017 — F-017 (FUSE mount) is cut, and the measurement is why.** The register's last undecided entry. Its own justification — "supersedes the separate, limited fuseadf... partially covered by the Linux AFFS driver" — did not survive being checked: the kernel driver handles `DOS\0`–`DOS\3` read **and write** and `DOS\4`/`DOS\5` read-only, which over a 400-image sample is **94% of the corpus read/write** and essentially all of the 77% that mount at all. For the ADF and HDF the clause names, a FUSE filesystem would reimplement a driver that has been in the kernel since 1993, with "no root required" as its only advantage.
  **The measurement changed the shape of the recommendation rather than confirming it.** What the kernel cannot read is real and is not F-017: an ADZ, an extended ADF, an SCP capture, a partition of an RDB device, a volume reconstructed from raw tracks. A mount of *those* would let ordinary tools reach content nothing else can, so it is on the candidate list with this measurement behind it instead of the one F-017 carried.
  **A second reason, independent of coverage:** a filesystem interface cannot express what ADE is for. `read()` returns bytes and has no way to say a file came from a volume reassembled out of flux with 3% of its sectors missing. Mounting is the one interface that must discard the reporting that is the point of the tool.
  F-017's number and section stay, recording the cut — a reader who finds it referenced lands on the reason rather than on nothing.

- **IMP-005 applied — an open image no longer costs its own size.** `ade-container::FileSource` is a `BlockSource` that reads each block from the file when asked, and `Image::open_lazy` uses it. The bridge opens that way because a front end holds every image it opens; the CLI still opens eagerly because it holds one and exits.
  **400 plain ADFs held open: 364 MB → 12.9 MB resident**, against 344 MB of images on disk. Twenty-eight times less, and now far *below* the files' own size rather than slightly above it — what remains is a file handle and an inspection each, about 32 KB per image. What the operating system caches is its own affair, reclaimable and shared with every other reader.
  **It cost 1–3% of time**, measured against a stashed build rather than assumed: over 60 images and 3,827 rows, expanding 35.1 s → 35.5 s, selecting 11.6 s → 11.9 s, searching 19 ms → 23 ms.
  **No `unsafe` and no dependency.** Memory-mapping is the obvious answer and is unavailable twice over — D-006 forbids `unsafe`, the workspace has no dependencies, and every mmap crate is one or the other. Positional reads (`read_at`, `seek_read`) are safe, in `std`, and enough. `RawImage::bytes()`, the whole-image escape hatch, turned out to have no callers at all, so the block seam really was the only path and nothing above had to change.
  **The trade is real and is tested.** An eagerly opened image is a snapshot; a lazily opened one is a window, and the file underneath can be truncated or replaced. `src/api/tests/lazy.rs` pins both halves: identical answers while the file is whole, an error or an empty listing rather than stale content when it is not, and `Image::open` still indifferent to the file vanishing.
  **One prediction in the entry was wrong, usefully.** It expected this to break the guarantee that a decompressed container behaves like a plain one. It does not: `open_lazy` sniffs the container and falls back to reading whole for anything whose blocks are not its file — gzip wrappers, flux captures, reconstructions — so the guarantee holds because the fallback is inside the call rather than left to the caller.
- **IMP-008** — new: a directory expansion costs about 9 ms, and it is not the bytes. Found needing a baseline for the above: expanding 3,827 rows takes 35 seconds whether the image is in memory or on disk, so what remains is most likely the fresh `Volume::mount` every ABI call performs. - **IMP-008 applied, and the guess in it was wrong — which is why it said to measure first.** A directory expansion cost 9.3 ms; the entry supposed a fresh `Volume::mount` on every ABI call was to blame. Measured: **mount is 0.002 ms and mount-plus-list is 0.017 ms**, five hundred times faster than the symptom. Nor was it the harness — expanding with and without `processEvents` between rows gave 9.35 ms and 9.31 ms.
  **It was one line of Qt.** The three fixed-width columns used `QHeaderView::ResizeToContents`, added on 2026-08-27 to stop the Modified column truncating to `1990-09-20 17:…`. That mode re-measures every row in the tree on every insertion, so expanding one drawer costs time proportional to the whole tree — quadratic, and invisible until there are thousands of rows. Over 60 images and 3,827 rows: **35,648 ms → 247 ms, 144× faster**, with the columns unchanged. A datestamp is always nineteen characters, protection always eight, a size on a floppy never more than seven digits, so the shape is measured once with `QFontMetrics` instead of re-measured forever. Verified by looking: nothing truncated.
  **The regression test is the widths, not a timing bound.** A timing assertion cannot catch this at fixture scale — 48 rows is far too few for a quadratic to show, and putting the bad mode back leaves it passing. The widths test fails, because `ResizeToContents` sizes to the content actually present and a fixture's short names are narrower than the widest value a column must fit. Both were checked by reintroducing the mode; the timing test was deleted rather than left implying a guard it does not give.
  **The fix the entry proposed would have bought two microseconds and cost a design** — caching a mounted volume on the handle, with the self-reference IMP-006 was glad to avoid.
- **IMP-009** — new, from separating IMP-008's two halves: selecting a directory takes 0.01 ms and selecting a file 3.6 ms, essentially all of it building a 64 KB hex dump into both views whether or not their tab is showing. Linear and bounded by what one person can click, unlike IMP-008's quadratic — recorded because it was measured, not because it hurts.

- **`ade create` — a blank formatted disk (F-019), and ADE's first write path.** Asked for while testing drag-out in the GUI, and the gap was real: ADE read six container formats and could create none, so there was no way to obtain a disk to put anything on.
  **D-004 permits this rather than being waived.** Its rule is that "every write path ships only after its read path is proven on fixtures", with write arriving "from Phase 4/5" — OFS/FFS reading is proven across 4,652 corpus images at 99.36% agreement with ADFlib, and this is Phase 5. It is also the safest write there is: a new file, never an existing one, which is the irreversible damage D-004 is actually about.
  **Written from SPEC, deliberately not from the fixture generator.** Reusing `ade-fixtures` would have been quicker and would have destroyed what makes it useful — D-010 keeps it dependent on nothing so a misreading in a layer crate cannot cancel out against it. There are now **three independent statements** of what a blank disk is, and the tests require all three to agree: ADE reads back what it wrote, the fixture generator's equivalent matches structurally, and **ADFlib mounts it** — verified for OFS and FFS, DD and HD, with the volume name, filesystem and size read back correctly by an implementation nobody here wrote.
  **The health check caught a defect immediately:** the first disk produced reported three `datestamp-day-zero` findings *against itself*, because the stamp defaulted to zero and SPEC records day zero as what Amiga software treats as unset. The command now uses the clock — "created" means when the disk was made — while the library still takes an explicit stamp so tests stay deterministic.
  **A blank disk is not bootable**, deliberately: AmigaDOS's own `format` leaves the boot code zeroed unless `install` is run, and ADE will not write boot code it would then refuse to interpret (AV-002). The bitmap has its own test, because a set bit means **free** — inverted, a fresh disk would report itself full, every checksum would still be valid, and nothing else would notice.

- **`ade scan` — content signatures (F-020).** Mapped across from the Atari Disk Engine, which has a 62-signature scanner ADE had no equivalent of. It searches the **whole image**, not just its files: what a directory entry calls a thing and what the bytes are often disagree, and on a damaged disk the interesting content is in space nothing points at any more. 4,652 images scan in 24 seconds.
  - **The table is measured, not recalled.** Every signature was checked against the whole corpus and the counts are in SPEC §Content signatures — 7,445 hunk executables across 677 images, 3,889 IFF, 1,686 ProTracker modules, 1,385 PowerPacker. Magics with no corpus hits are recorded as **untested** rather than quietly trusted.
  - **Three rules the corpus taught, each correcting a confidently wrong answer.** Magics are **anchored to block starts**, because a file's header lands there and a four-byte substring search over 4.2 GB does not; the exceptions are markers inside a file, like a ProTracker `M.K.` 1,080 bytes in. The **most specific match at an offset wins**. And a pattern **repeating across consecutive blocks is filler, not files** — which turned 91 reported "DMS archives" into 3 real ones plus one damaged disk.
  - **It found damage the catalogue had missed.** `DMS!!ERR` and `DMS!1.52` are not archives: they are what **xDMS writes over a track it could not decompress**, so an ADF carrying either came from a DMS that failed partway. **Nine corpus images carry it** — three Cannon Fodder 2 disks, Crystal Dragon, Heimdall 2, Lemmings, Super Tennis Champs, Powerstyx and a 1986 Workbench. A report that simply stops reads as "there is nothing more to know". The `(AGA)` in a TOSEC name is labelled as the *catalogue's* claim rather than borrowed as the disk's.

- **Block map visualisation in the GUI (F-027).** A **Map** tab showing the disk as a grid of blocks coloured by region. The hex pane answers "what is at this offset" a screen at a time and the health report gives counts; this answers "where did the space go" at a glance. F-022 had already built the data and proved it tiles exactly, so it really was a widget over what was there.
  - **Files are coloured here and are not in the hex pane** — the one deliberate divergence. Under text being read, tinting four fifths of a disk distinguishes nothing; on a map every cell is a block, and leaving files blank would leave the map empty.
  - **The colours were solved rather than chosen.** At the first values `unclaimed` sat at **1.16 contrast** against the page, which made "empty" and "off the end of the disk" the same picture — measured, not noticed by eye. The chosen mix holds in both themes (dark: file 3.93, empty 1.39, 2.82 between; light: 2.27, 1.41, 1.61), and the test asserts the ratios so they can be retuned.
  - **A cell covering many blocks shows the most structural one**, because showing the commonest would erase a rootblock that is one block in seventeen hundred. The tooltip then says `blocks 640–703` rather than naming one of them.
  - **Selecting a file picks out its blocks** without clearing the map, which is the thing no listing can show: where a file actually lives, and how scattered it is.

- **Saving a modified disk and creating a directory on one are on the roadmap** (requested 2026-09-01), in the write-suite entry of the Atari feature map and as a Phase 5 deliverable. Both are blocked on a **decision entry rather than on effort**: D-004 permits a write path once its read path is proven, and OFS/FFS reading is proven across 4,652 images, but writing into a disk somebody owns is the damage D-004 exists to prevent.
  - The entries are written to be built from rather than to be a placeholder. The load-bearing idea is that **edits should be buffered and written only on an explicit save**, which turns "never-reversible in v1" from a reason to refuse the suite into a property the design already has: nothing touches the file until asked, closing without saving costs nothing, and undo is a stack in memory rather than a promise about a file. Save As then falls out for free.
  - Creating a directory is recorded as the right *first* write: one block, one hash-table insertion, one bitmap bit — and the first operation that has to **maintain** what the reader checks rather than merely satisfy it, since the hash slot depends on international hashing (C-006) and a dircache volume needs the parent's cache updated or the health report will call the new block orphaned. It is also verifiable end to end, because ADFlib can be asked whether the directory is there.

- **Fixed BUG-010: a file that is not a disk image is no longer opened as a hard disk.** Reported from the window — dragging three files out of a disk and dropping them back opened two Amiga executables and a level file as damaged hard disks, three rows each explaining nothing.
  - The sniffing cascade ended by calling **anything** that was not an exact floppy geometry a hardfile. But a hardfile is a raw volume — bootblock, rootblock, bitmap — so its first three bytes are `DOS` (SPEC §Hardfiles). Size alone is the *absence* of evidence, and the fallback was treating it as the presence of some.
  - **The whole corpus is classified identically**: all 7 images detected as hardfiles begin `DOS`, the container counts across all 4,652 are unchanged, and mounted (3606) and sound (2850) are unmoved.
  - New ABI predicate `ade_image_recognised`, because a front end must tell "no kind of disk image" from "recognised and holds no volume". A DMS archive is the second and is worth opening to say so (IMP-006); an executable is neither, and now gets one message instead of a row. An unformatted 901,120-byte file stays recognised — the right size makes it an ADF even with nothing in it.

- **Fixed BUG-009: a disk with extra cylinders is no longer unmountable.** ADE computed the rootblock from the *file's* block count, which on an 81-, 82- or 83-cylinder image lands at the midpoint of the file rather than of the volume — block 902 for a 1804-block image, where it found a file header and reported no volume. A volume can be smaller than the file that holds it.
  - `volume_geometry` tries the file's own geometry first, so every image that mounted before mounts identically, and only then the standard floppy shapes **largest first**, adopting one only when the file can satisfy it *and* a real rootblock is at its position. It can rescue an image but never invent one. Largest-first matters: tried the other way, an oversized HD image would be claimed as a DD volume the moment block 880 held something rootblock-shaped, and on an HD disk that block is ordinary data.
  - **Measured across the whole corpus: 5 images began mounting, 0 stopped.** 3601 → 3606 of 4652. `Chambers of Shaolin_Disk2` is `CHAMBER OF SHAOLIN - QUARTEX`, `Lingo` is `LINGO`, `Preis ist Heiss, Der` is `Der Preis ist heiss`, `Universal Monsters & Superhero` is `THE ONE (B)`, and a Workbench 1.4 alpha with a non-block-aligned size is `Workbench1.4A15`.

- **`ade create` writes every disk type ADE can verify (F-025).** Six filesystems and four geometries, up from two and two: `--type=ofs|ffs|ofs-intl|ffs-intl|ofs-dc|ffs-dc`, and `--hd`, `--dd525` or `--size=N` for an unpartitioned hard disk.
  - **The set is closed, which is why "which ones" is answerable.** `DOS\0`–`DOS\7` is the whole AmigaDOS registry — surveyed in SPEC across four sources, re-checked online, and no source anywhere knows a `DOS\8`. Six are written; `DOS\6`/`DOS\7` (LNFS) are refused **by name with the reason**, because D-013 defers them on verifiability and somebody asking for something real deserves better than "unknown type".
  - **The dircache question was settled by the oracle rather than assumed.** SPEC records the pointer as "first dircache block, else 0", leaving open whether a blank `DOS\4`/`DOS\5` needs one. It does not — ADFlib mounts one written with a zero pointer, and all twelve type-and-size combinations are now checked against it.
  - **Hard disks needed multi-block bitmaps.** One bitmap block maps 4,064 blocks, so 8 MB needs five, matching SPEC's arithmetic exactly; the rootblock's `bm_pages` array is filled rather than just its first entry. Past 25 pointers a `bm_ext` chain is needed, which ADE does not write: refused, because a volume whose bitmap is partly described reports free blocks that are not. The boundary is exact — 49 MB fits, 50 does not.
  - **A corpus measurement removed a feature and found a bug.** `--cylinders=N` was written, then dropped: five of the six non-standard floppy-sized corpus images keep their rootblock at **880**, so an 81-, 82- or 83-cylinder image is an ordinary 80-cylinder filesystem in a longer file, not a larger volume. Writing one would have produced a file matching no real disk. It also means ADE cannot currently mount those five — logged as **BUG-009** rather than fixed inline, since it is a read-path defect this work uncovered.
  - ADFlib was the signal both times, and the two failures read differently: `adfReadRootBlock : id not found` for the extra-cylinder disk, where it mounted the device and disagreed about the contents, against `adfMountDev : unknown device type` for 5.25", where it refuses the size before reaching any filesystem. The first was a fault; the second is a gap in the oracle, and 5.25" ships on two of the usual three checks with that said rather than counted as a pass.
  - 574 → 585 Rust tests.

- **`ade extract --all` and the GUI's Extract all files (F-024).** Every file on an image into a folder, with its drawers. `extract` took one path at a time and the GUI extracted one dragged file; whole-image extraction existed nowhere, which is the ordinary thing to want from a disk.
  - **Every naming rule came from a measurement**, not from a preference. Across 4,652 images and 83,487 distinct filenames: non-ASCII names are real and meaningful (`Effekte für AE 2 Deutsch.info`, `CD³²_Prefs`), so Latin-1 is decoded to UTF-8; three names carry a NUL, which cannot go in a POSIX filename at all; **zero** contain `/`; one is exactly `.` or `..`; three contain a literal `%`. Those are escaped `%XX` of the original byte, `%` included so the escape stays reversible — for a file taken off a disk this is the only record of what its name was.
  - **And what is deliberately left alone**: 62 names carry a Windows-illegal character and 328 end in a dot or space or are nothing but spaces. Legal on POSIX, and escaping them would mangle 390 real names to buy portability to a platform ADE has never been built on. The numbers are recorded so a Windows build can take that decision with the cost in front of it.
  - **Nothing is ever overwritten.** A collision means a case-insensitive host or two names that escaped alike — exactly one corpus image collides that way, `1869 (AGA)_Disk1` with `Startup-sequence.bak` and `startup-sequence.bak` in one drawer. The second is skipped and named, and the exit code says the recovery was partial: reporting success while quietly missing a file is how somebody comes to believe they have the whole disk.
  - Over 400 corpus images: **14,995 files written in one second, 2 skipped** — both genuine read errors on one damaged disk, each named. Nothing stops at the first bad file, the same reasoning as `ade batch`.
  - A hard link is resolved before it is read; reading one directly gives an empty file of the right name, silently (BUG-005). Verified against the single-file path: all 49 files of `4-Get-It.adf` are byte-identical taken one at a time or all at once.
  - Two things learned on the way. `("extract", 2)` matches both `<image> <path>` and `<image> --all <dir>`, and match arms are tried in order — with the `--all` arm second it was silently ignored and the destination was read as a path on the disk (`no such entry: tmp`). And `read_file` **clamps** an oversized declared payload rather than failing, which is BUG-003's fix working as designed and which quietly invalidated the first attempt at a damaged-file test.
  - New ABI: `ade_unpack`, exercised from C in the smoke test — twice over the same folder, so the never-overwrite promise is checked rather than asserted.

- **Content search in the window (F-023).** The GUI's search box gains a **Contents** mode beside its existing **Names**: the bytes of every open image, including the parts no file occupies. F-021 had been command-line only, and the window could not search contents at all.
  - **One box, two questions.** A mode selector rather than a second field, which would leave one of them stale whenever the other was used. The results columns follow the mode — an offset and a filename are not the same answer.
  - **A refused pattern is not a search that found nothing.** `ade_find_open` returns a handle carrying the reason rather than null, the only opening call in the ABI that does: "0 matches" for a pattern that was never searched would have someone conclude their disk is clean. The same distinction the command line draws with exit 2 against exit 1, and the reason the contract is documented as *never null* rather than left to convention.
  - **Clicking a hit goes to it** in the whole-disk view, scrolled with three lines of lead and the byte highlighted — a match on the first visible line reads as the top of the view rather than as a result. F-022's colouring pays off here: the byte arrives in a region the eye can already name, and the tree marks the owning file.
  - `Search::of_image` searches through an already-mounted handle instead of mounting a second copy from bytes — a whole extra copy of the disk and a second walk of its directory tree. A test pins both entry points to the same answer.
  - Noticed while looking at it: a hit is attributed **by block**, so searching a real disk for `SUPERSHEET` reports one inside `FONTSET`, a 20-byte file. The string is in the unused remainder of the 512-byte block that file occupies. True at block granularity, and worth knowing before reading too much into an attribution.
  - New ABI: `ade_find_open/count/match/was_hex/error/free`. Schema **1.8 → 1.9** for `matches[].file_block`, so a hit can name the entry that owns it and not only its path.

- **A Help menu with an About box (F-004).** Version from `ade_version()`, not from a string written in Qt — an About box is the one place people go to find out exactly what they are running, and a front end's own version string can disagree with the library it was built against. The licence line repeats NOTICE's "no third-party code", which has to change if D-009 ever brings xDMS in; a test pins both that and the version. The text is exposed as two static functions so the test can read what the box would say without opening it: `QMessageBox::exec` blocks, and a test that dismisses a modal to inspect it hangs the suite the day the dialog changes. The menu holds **About and nothing else** — the manual will join it, and a greyed-out placeholder is a promise the window has already broken.

- **Scrolling the whole disk says which file is on screen (F-022).** The owning row is marked in the tree and named in the status bar as the hex view scrolls through it.
  - **Qt does not reliably say when the view moved.** A click in the scrollbar **trough** scrolled the pane from line 0 to line 37 — the painted text proves it moved — while emitting `valueChanged` zero times and calling `scrollContentsBy` zero times; the wheel and a drag of the handle both notify, which is why the gap read as the feature working until somebody paged down. Reported, reproduced, and fixed with a 120 ms poll alongside the signal, skipping its work unless the top line changed. The first two attempts at this were wrong and are worth recording: `cursorForPosition` reads where the viewport has been *painted* and lags the scroll, and `scrollContentsBy` — the virtual that exists for exactly this — is simply not called on that path.
  - **Marked, not selected.** Selection is what chose the whole-disk view, so following the scroll with it would replace the very view being scrolled — the feature would undo itself on the first wheel click. The test that matters here asserts the selected row is still the disk.
  - The mark is a pale wash **and bold**. The wash alone is a paler version of the selection colour, and the selected row is right there in the same tree: rendered side by side they read alike, which was visible the moment it was looked at.
  - **The status bar names the path even when no row can be marked.** A file inside a drawer nobody has opened has no row, and "file" on its own says nothing — found by scrolling to offset 890,000 on a real disk and getting exactly that. The tree is deliberately not expanded to reveal it: one that reorganises itself under the pointer while you scroll is worse.
  - The map now carries the owning entry's **block** as well as its path, and the row search is **scoped to the image and partition on screen**. A block number is unique within a volume and nowhere else, so an unscoped search would have marked a file in whichever open disk held that block first. Schema **1.7 → 1.8** for `spans[].file_block`.
  - The tree's role constants moved to `MainWindow.h`, because a test that checks the right row was marked has to ask the row which block it is, and a second copy of `Qt::UserRole + 1` in the test is a copy that can drift.

- **`ade layout` and a whole-disk hex view with coloured regions (F-022).** Mapped across from the Atari Disk Engine, which shows the full disk with its sections colour-coded. A file view can never reach the bytes that matter most on an old disk: the bootblock where protection lives, the rootblock, and the space no directory entry points at. Selecting an image's own row in the GUI now shows the whole disk, each region tinted, with a legend naming only the regions that disk actually has.
  - **The map is a tiling, not an annotation.** Spans cover every byte with no gaps and no overlaps — a front end colouring from a partial map paints holes that read as ordinary data, so the map being wrong would look exactly like the disk being different. **4,651 of 4,652 corpus images tile exactly, in 6.6 seconds**; the one exception is a 166-track extended ADF whose assembled size matches no geometry, which `ade ls` has always refused the same way. The mounted count, 3,601, matches `ade batch`'s independently.
  - **Files are deliberately not coloured**, because they are most of a disk and colouring everything is the same as colouring nothing. Unclaimed space gets the faintest wash there is: "not part of any file" is worth seeing and is also the second most common answer.
  - **F-021's region attribution moved into `ade_core::layout` and `find` now uses it**, so a single hit and the whole-disk map can never disagree about what a block is. That was two copies of the same walk before this.
  - **Only whole images.** A device's map would place several volumes, each with its own block size, at absolute offsets, and no corpus image carries an RDB — `ade_layout_open` returns null for a partition index rather than guessing at something unverifiable.
  - New ABI: `ade_layout_open/count/span/free`, `ade_region_name/describes`, and `ade_image_read` for raw bytes of the *mounted* image (an ADZ's decompressed disk, a flux capture's reconstruction — the only space in which a span's offset means anything). The region strings are spelled out in the bridge as NUL-terminated literals rather than allocated per call, and a test pins them equal to the engine's so the duplication cannot drift.
  - The whole-disk view is capped at **4 MB**, measured rather than chosen: every corpus image is smaller (the largest is 2.1 MB), so every floppy and extended ADF is shown whole and only a hard disk is cut. Clicking the disk row costs 406 ms, returning to a file 26 ms.
  - Schema **1.6 → 1.7** for the new document. 545 → 558 Rust tests (24 of them across the ABI), 30 → 39 GUI tests.
  - Three traps, all found by tests rather than by looking. A `QSyntaxHighlighter` **re-highlights its whole document when its inputs change**, so the map goes in before the text over a cleared pane — set afterwards it cost eleven seconds on a 56,000-line dump and briefly painted the new disk in the old one's colours. `QTreeWidget::setCurrentItem` can move the **current row without moving the selection**, after which the window redraws whatever is still selected — which looked exactly like a failure to clear. And a whole-line background is split by Qt into fragments wherever a foreground is set on top, so a test looking for "one range covering the line" finds nothing while the colour is plainly there.
  - One real defect caught on the way: selecting a file with no readable contents returned early without clearing the map or the legend, leaving the previous disk's colours under the words "(no readable contents)". The clearing now happens before the branches, because it has to happen on all of them.

- **Atari Disk Engine feature map** in ROADMAP.md, surveyed 2026-08-30 against the predecessor at 23,220 lines. One-directional by request — what the Atari engine does that ADE does not — and it separates the difference that is a **gap** from the difference that is a **decision** and the difference that is simply a **different format**. Ten candidates, none scheduled, each sized with the constraint it runs into; three need a DECISIONS entry before any code. Written down because the same map was made on 2026-08-29, produced F-019, F-020 and F-021, and left its unbuilt half recorded nowhere.
  - Some of the difference is now recorded as **answered rather than missing**: writing a bootblock stays declined (AV-002's defence is structural, and it is the one operation that would make ADE a vector rather than a reader), theme menus stay declined (the GUI takes the desktop's palette, which is why the hex pane blends its colours from it), and FAT repair is not applicable to a filesystem with no FAT.
  - The two largest differences are both prior questions rather than work: a **68000 disassembler** (4,672 lines there) asks whether a disk engine is where a disassembler belongs, and a **Lua console** (3,119 lines, vendoring `sol`) asks the zero-dependency posture its largest possible exception — where `--format=json` already makes ADE scriptable in whatever language the user has.
  - The reverse list is longer and is stated too, along with the measurement that matters most: the predecessor is a **4,237-line class with 75 methods**, measured today, which is what D-003 exists to prevent.

- **The GUI window opens at the size its contents need (F-004).** It opened at a hardcoded 1100x700 with an even split, which gave the hex pane about 550 pixels for a dump line measuring 78 monospaced characters: the characters column was cut off on the first disk anybody opened, and the remedy was to resize the window by hand every time. Both halves are measured now, the way the tree's fixed columns already were — from the text they must hold, in the font they will hold it in, so a machine whose fixed font is a different size gets a different window rather than the same bug.
  - **An even split sounds fair and is not.** The tree's content has a natural width and the hex pane's does not, so half the window is more than the tree can use and less than the dump needs. The tree keeps what its columns need; every extra pixel goes to the pane showing the disk.
  - **Clamped to the screen**, because a measurement is not permission to be bigger than the display — the same fault in the other direction, and worse, since a window wider than the desktop can put its own edges out of reach. When there is not room for both, the **tree** gives way to a floor still wide enough to read a name in: a long filename elides and is still a filename, where a clipped dump line is simply missing.
  - A splitter **redistributes a resize among its children**, so sizes set before the resize are proportions the next resize spends — `setSizes` has to come after `resize`.
  - **Neither test names a pixel width**, because the fixed font is whatever the desktop calls fixed-width and is not the same size twice: one dump line measures 563px under the offscreen platform and 609px on the development display. A test written around 1100x700 passed in CI and failed on the desk — which is how the first version of it was caught. One test gives the window room to spare and checks the split spends it on the pane with a content width; the other checks the window asks for that room itself, and **skips** where the screen cannot hold a dump line beside a usable tree, as the offscreen platform's 800x800 cannot.

- **The GUI hex pane's selection stays in one field (F-004).** A hex dump is three columns pretending to be one line of text, and ordinary text selection does not know it: dragging down two lines in the hex field took the end of that line's hex, the ASCII column, the next line's offset, and only then more hex — so copying a screenful of hex was impossible, which is one of the two things anybody does with a hex view. A drag is now clamped to the field it started in, including when the pointer wanders out of it, and copying returns what was highlighted and nothing else, one clipboard line per line on screen.
  - **A selection in one field marks the same bytes in the other.** Hex and characters are two readings of the same bytes, and which bytes is the question a hex view exists to answer. The mark is a paler wash with the text colour untouched — so a dimmed null stays dimmed under it — and is deliberately weaker than the selection: painted alike, both fields would look equally selected and nothing on screen would say which one Ctrl+C copies, replacing one ambiguity with a worse one. Selecting offsets marks nothing, since that selects whole lines and marking every column of every line adds nothing to the highlighted offsets.
  - **What clamping took away is back in the context menu.** Copying a line as it appears, offsets and all, is what somebody pasting into a bug report wants, so "Copy Whole Lines" sits beside "Copy" rather than behind a modifier key nobody would guess.
  - `copy()` and `selectAll()` are **not virtual**, so the base class's shortcut handling cannot be redirected into an override — Ctrl+C, Ctrl+A and the context menu are intercepted instead. The standard context menu would have given an empty clipboard, since the selection this pane draws is not the document's.
  - Keyboard selection with shift and the arrow keys is deliberately unchanged: making it agree would mean reimplementing cursor movement over a layout the document does not describe, and the drag is where the problem bites. Four tests drive real press/move/release events — to the **viewport**, which is where a scroll area's mouse events arrive; sent to the frame they reach no handler and the test passes on an empty selection.
  - 20 → 30 GUI tests, three of them checking the mark — verified by removing it, which fails two of the three.

- **Null bytes dimmed in the GUI's hex field (F-004).** Carried over from the Atari Disk Engine: on a disk that is mostly padding, dimming the zeros is what makes the data visible. ADE's hex pane is a `QPlainTextEdit` rather than a hand-painted widget, so it is a `QSyntaxHighlighter` over the document — which also means Qt only ever re-highlights the lines on screen rather than all 4,096 of a 64 KB preview.
  - **Placed by column arithmetic, not by searching for `00`.** A text search dims the `00000000` offset at the start of every line and any `00` a file happens to contain in the ASCII column — the opposite of making data stand out. The test asserts exactly this, on a line rigged with all three traps at once, and was checked by reintroducing the naive version: it dims three places instead of one.
  - **The grey is blended from the palette**, 70% from text toward background, rather than the Atari engine's pair of constants chosen by a hand-written light/dark test. That gives (178,178,178) on a standard light theme against its (180,180,185), and 97–105 on the dark backgrounds desktops use against its 100 — the same choice, on any palette.
  - `hexview::dump` moved out of `MainWindow.cpp` to sit beside the highlighter in `gui/src/HexView.{h,cpp}`, because the highlighter has to know the dump's layout and, kept apart, a change to one would silently misplace the other. 18 → 20 GUI tests.

- **`ade find` — content search (F-021).** The companion to `scan`: that one answers "what is on this disk that I did not know about", this one answers "is *this* on it" — a string, a filename, an opcode, a copyright notice. Text or hex, decided from the pattern's shape, over the whole image rather than over its files. A search of an 880 KB disk takes 3 ms.
  - **The hex-or-text guess is made, and made visible.** Entirely hex digits and separators, pairing into whole bytes, is read as bytes; anything else is text. The rule catches a few English words — `dead`, `face`, `added` — and that is the deliberate direction, because the opposite mistake is silent: someone searching for `60 1A`, getting the ASCII of "60 1A" and finding nothing concludes the disk is clean. This mistake announces itself, `hex: true` in the output, and `--text` reverses it. The unit test for overlapping matches originally failed on exactly this, with `aa`.
  - **A measurement changed the design, and then corrected it.** `Copylock` appears on **103 of 4,652 corpus images**, and the region turns one string into four findings: **bootblock** on 86, where protection and its trackloader live and no directory entry points; **rootblock** on 10, because those disks are literally *named* `Copylock(tm) Amiga`; **unclaimed** on 11; inside a **file** on 5. The first implementation called all of them "unallocated" — wrong about the most deliberately written block on the disk, and wrong about a volume name. The bootblock is now named **even when the volume does not mount**, C-008 in the place it matters most, since a protected disk is frequently the one that fails to mount.
    The first version of this note said "every hit is in block 0". That was measured over the alphabetically first 500 images, where it happens to be true; over the whole corpus 51 hits are elsewhere. A sample that agrees with the design is the easiest measurement to stop early, and the rootblock hits — the ones the short sample missed — are the best evidence the regions were worth having.
  - **Occurrences are not disks, again.** `DOS` matches **7,833,991** times across the corpus, 207,159 of them on one image filled end to end with `DOS\0` — an occurrence count describes that image and little else. Counted by image: **4,450 of 4,652**, bootblock 4,359, file 1,317, unclaimed 840, directory 55, rootblock 37, bitmap 14. The same trap as the batch histogram. The 207,159 looked impossible and was checked against `grep`, which agreed — the sweep was right and the two minutes were still worth spending.
  - Overlapping occurrences are all reported, because a caller counting a repeating sequence would otherwise be told a number that is quietly low. Text output shows twenty and says how many it held back; JSON carries every one. Nothing found exits **1** as `grep` does; a malformed pattern exits **2**, so "searched, found nothing" and "never searched" cannot be confused. Schema **1.5 → 1.6** for the new document. 545 tests.
